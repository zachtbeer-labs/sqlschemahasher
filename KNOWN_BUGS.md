# Known Bugs — Schema Hash Fidelity

Findings from a hash-bug-hunter audit of `SchemaExtractor`, `SchemaMetadata`, `SchemaHashCalculator`, and `SchemaHashOptions`. Ranked most-severe first. "False negative" = two schemas that should hash differently hash the same (silent collision). "False positive" = the same schema can hash differently across runs/environments (spurious diff).

## 1. Column order is discarded (false negative)

**Location:** `SchemaExtractor.cs:109,318` (extraction sorts columns `OrderBy(c => c.Name)`); `SchemaHashCalculator.cs:83,230` (hasher re-sorts by name again). `column_id` is never captured.

Two table-valued types differing only in column order hash identically:

```sql
-- DB1
CREATE TYPE dbo.OrderLine AS TABLE (Sku NVARCHAR(20), Qty INT);
-- DB2
CREATE TYPE dbo.OrderLine AS TABLE (Qty INT, Sku NVARCHAR(20));
```

This matters most for UDTTs/TVPs, where parameters are marshaled **positionally** — these are genuinely different types, not equivalent ones. The same collision applies to ordinary table columns (`SELECT *`, column-list-less `INSERT`). Fix is free: sorting by `column_id` is just as deterministic as sorting by name, and preserves the information instead of discarding it.

**Confidence:** High for the collision. Whether ordinary (non-UDTT) table column order should also be preserved is a scope question — see bottom.

## 2. Identity seed and increment never captured (false negative)

**Location:** `SchemaExtractor.cs:63-71` selects only `idc.name AS IdentityColumn` from `sys.identity_columns`; `SchemaMetadata.cs:13` stores only the column name.

```sql
-- DB1
CREATE TABLE Invoice (Id INT IDENTITY(1,1) PRIMARY KEY);
-- DB2
CREATE TABLE Invoice (Id INT IDENTITY(1000,5) PRIMARY KEY);
```

Same hash. `sys.identity_columns` also exposes `is_not_for_replication`, also unread.

**Confidence:** High.

## 3. Disabled / untrusted CHECK and FOREIGN KEY constraints are indistinguishable (false negative)

**Location:** `SchemaExtractor.cs:167-187` — FK and CHECK branches select name/definition/actions but never `is_disabled` or `is_not_trusted`. `ConstraintSchema` (`SchemaMetadata.cs:46`) has no field for them.

```sql
-- DB1
ALTER TABLE Child WITH CHECK ADD CONSTRAINT FK_C FOREIGN KEY (PId) REFERENCES Parent(Id);
-- DB2
ALTER TABLE Child WITH NOCHECK ADD CONSTRAINT FK_C FOREIGN KEY (PId) REFERENCES Parent(Id);
ALTER TABLE Child NOCHECK CONSTRAINT FK_C;
```

Same hash, despite the second having **no enforced data-integrity guarantee** and different optimizer trust behavior (`is_not_trusted = 0` is required for the optimizer to rely on a constraint). Same issue for disabled CHECK constraints.

**Confidence:** High.

## 4. Constraint names are unconditionally dropped, with no option to preserve them

**Location:** `SchemaExtractor.cs:194-199` builds `ConstraintSchema` from only `(Type, Keys)`; the constraint name (selected at `:161`/`:168`/`:178`/`:184`) is used only for grouping, then discarded. `SchemaHashCalculator.cs:175-180` hashes only type + keys.

Renaming `CK_Age_Positive` → `CK_ValidAge` (same expression) produces no hash change. This is inconsistent with index handling, where name is a first-class configurable dimension (`IgnoreIndexNames`, `NormalizeAutoGeneratedIndexNames`). Constraint names appear in violation error messages, so applications can depend on them. Also: a user-named CHECK vs. a system-named one (`sys.check_constraints.is_system_named`) is invisible.

**Confidence:** High that names are dropped; medium on whether this is a bug vs. intentional — needs an explicit ruling.

## 5. SQL-Server-rendered definition text is a cross-version spurious-diff risk (false positive)

**Location:** Definition strings pulled straight from catalog views and hashed verbatim: computed column `cc.definition` (`SchemaExtractor.cs:94`), default `dc.definition` (`:179`), check `cc.definition` (`:184`), index `filter_definition` (`:125`).

SQL Server re-renders these expressions itself (parenthesization, built-in casing, `(getdate())` vs `getdate()`, numeric literal formatting), and rendering can differ across major versions/CUs. The same DDL script run on SQL 2019 vs. 2022 could hash a computed column or default differently even though nothing semantically changed — undermining the library's cross-environment comparison use case.

**Confidence:** Medium — the mechanism is real and documented SQL Server behavior; not verified against two live instances with a specific rendering delta.

## 6. Encrypted stored procedures all collapse to the same definition hash (false negative, edge)

**Location:** `SchemaExtractor.cs:226-227` — `HASHBYTES('SHA2_256', ISNULL(m.definition, ''))`. For `WITH ENCRYPTION` procedures, `sys.sql_modules.definition` is `NULL`, so `ISNULL` yields `''`, and every encrypted proc hashes to the hash of the empty string.

Two different encrypted procedures (or an encrypted proc whose body changed) with identical name + parameter signature hash the same — body changes are invisible.

**Confidence:** High on the mechanism; low real-world prevalence.

## 7. Column storage/semantic flags not captured: `is_sparse`, `is_rowguidcol` (false negative, lower severity)

**Location:** columns query `SchemaExtractor.cs:83-102`; `ColumnSchema` (`SchemaMetadata.cs:28`) reads nullability/computed/collation but not sparse/rowguidcol flags.

A `SPARSE` column vs. a non-sparse column of the same type collide; a `ROWGUIDCOL` marker collides. Sparse changes storage and NULL semantics; ROWGUIDCOL is a real column attribute.

**Confidence:** High that the fields exist and aren't read; medium on how much consumers care.

## 8. Data type / parameter type schema-qualification not captured (false negative, edge)

**Location:** `SchemaExtractor.cs:99` (`ty.name` only for columns), `:258` (`t.name` only for parameter types) — no `SCHEMA_NAME(ty.schema_id)`.

Two alias/CLR/table types named `IntList` in different schemas (`dbo.IntList` vs. `staging.IntList`) used as a column or TVP parameter type produce the same captured type string (`"IntList"`). Also, an alias scalar type's underlying base type (`CREATE TYPE ... FROM DECIMAL(9,2)`) is never captured as an object, so changing the alias's base type doesn't change any hash.

**Confidence:** Medium — real for user-defined types; built-in types unaffected.

## Scope-boundary questions (confirm intentional vs. bug)

1. **Table (non-UDTT) column order** — deliberately normalized away, or should ordinal be preserved? (For UDTTs, this is arguably a real bug — see #1.)
2. **Constraint names** — intentionally never hashed (#4)? Indexes get configurable name handling; constraints get none.
3. **Views, triggers, sequences, scalar/table-valued functions, synonyms** — none are extracted. `ExtractStoredProceduresAsync` filters `p.type = 'P'` only, so functions are entirely unhashed. Confirm this is an intentional scope exclusion.
4. **Temporal tables, memory-optimized tables, partitioning, filegroup/data-space placement, index `fill_factor`/`ignore_dup_key`/`is_padded`/`is_disabled`, `is_not_for_replication` on FKs** — presumably out of scope; confirm.
5. **Cross-collation environment comparison** — every string column emits its explicit `collation_name`, so two databases identical except for server default collation will diff on every string column (sibling issue to #5 above). Confirm this sensitivity is desired rather than noise.

## What was checked and found clean

- **Dapper positional tuple mapping** — every query's `SELECT` column order matches its tuple field order across all extraction queries; no silent mis-mapping.
- **Determinism of collections** — tables, columns, indexes, constraints, procs, UDTs are all re-sorted with `StringComparer.Ordinal` in the calculator; SQL `ORDER BY` (collation-dependent) is harmless because everything is re-sorted in C#. Parameters are intentionally kept in `parameter_id` (positional) order — correct. LINQ `OrderBy` is stable, so tie-equal effective indexes stay deterministic.
- **Length-prefixing** — `AppendString` (`SchemaHashCalculator.cs:280-289`) length-prefixes little-endian; the `"AB"+"C"` vs `"A"+"BC"` ambiguity class is handled. Trailing optional blocks (COLLATION/COMPUTED/FILTER/DIR) are gated on presence, so absent-vs-empty is unambiguous.
- **`IsAutoGeneratedName` / `GetEffectiveIndex` / option precedence** — `IgnoreIndexNames` correctly wins over `NormalizeAutoGeneratedIndexNames` (`:146-148`); presets (`V1`/`V2`/`Structural`) set the flags their docs claim. The GUID/hex heuristic (`>=16` chars, multiple of 8) is opt-in and documented as heuristic.
- **FK actions, collation, param direction** (addressed in commits `f21d97a`, `7869887`) are captured and hashed correctly, and are covered by tests.
