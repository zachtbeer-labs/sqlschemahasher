## Build Commands

This is a .NET 9 class library with integration tests. The solution file is `SqlSchemaHasher.sln` at the repo root.

```bash
dotnet build SqlSchemaHasher.sln
dotnet test SqlSchemaHasher.sln
dotnet pack src/zachtbeer.SqlSchemaHasher.csproj -c Release
```

Integration tests use Testcontainers to spin up SQL Server 2025 in Docker. Docker must be running to execute tests.

**Running the tests — delegate to the `test-runner` subagent.** When you need to run the integration suite (after a change, before committing, to check the build, or to verify a specific area), invoke the `test-runner` agent via the Task tool instead of running `dotnet test` yourself. It handles the Docker/Testcontainers bootstrap, keeps the ~193-test output out of your context, and returns a structured pass/fail report; it can also infer and run a subset from your wording. Run `dotnet test` directly only when the subagent is genuinely unavailable.

## Architecture

This library computes deterministic SHA256 hashes of SQL Server database schemas for change detection and environment comparison. It is published as the `zachtbeer.SqlSchemaHasher` NuGet package.

Minimum target server: **SQL Server 2016 (13.x) / Azure SQL**. Extraction reads catalog columns introduced in 2016 (temporal `temporal_type`/`generated_always_type`, `sys.masked_columns`, `encryption_type_desc`), so older servers are not supported. In scope: tables, stored procedures, user-defined table types, views (including indexed-view indexes), T-SQL functions (scalar, inline TVF, multi-statement TVF), DML triggers, sequences, synonyms, and extended properties (database-, schema-, object/column-, parameter-, index-, and table-type-scoped). Out of scope: scalar/CLR user-defined types, CLR modules (functions/triggers/aggregates), DDL/database/server-scoped triggers, extended properties on constraint objects (system-generated constraint names are not deterministic across databases), and newer-version-only features (ledger, graph node/edge, SQL 2025 vectors).

### Core Flow

`SqlSchemaHash` (static facade) → `SchemaExtractor` (SQL queries via Dapper) → `SchemaMetadata` (immutable records) → `SchemaHashCalculator` (deterministic SHA256)

### Key Classes

- **`SqlSchemaHash`** — Static public API, the library's *only* public entry point besides `SchemaHashOptions`, `SchemaHashResult`/`SchemaHashComparison`, the five normalization enums, and the `SchemaMetadata` record family. All consumer-facing methods live here. Returns a versioned envelope `<version>:<base64hash>` (hex internally, converted and wrapped at the boundary). Parse and compare envelopes with the `SchemaHashResult` record.
- **`SchemaHashResult`** — Parsed envelope record (`Version`, `Hash`) with `ToString`/`Parse`/`TryParse` and a static `Compare` returning `SchemaHashComparison` (`Equal`/`Different`/`Incomparable`). Lets consumers distinguish "schema changed" from "library version changed" (differing version ⇒ `Incomparable`). The envelope deliberately does **not** encode the comparison options; hashes computed with different options produce different hashes and compare as `Different`, so callers must use matching options (same discipline as matching library version).
- **`SchemaExtractor`** — `internal` (not part of the public API surface). Runs batch queries against `sys.*` catalog views to extract tables, stored procedures, user-defined table types, views, functions, triggers, sequences, synonyms, and extended properties. Columns and constraints are keyed by catalog `object_id` (a table's `object_id` and a table type's `type_table_object_id`) and distributed to their owning container, so one pass over the constraint views covers both tables and table types; the same technique distributes indexes to both tables and indexed views (`sys.objects` driven, `type IN ('U', 'V')`). Stored procedure and function parameters share one `(SchemaName, Name)`-keyed pass (`sys.objects` driven, `type IN ('P', 'FN', 'IF', 'TF')`) since procs and functions share the schema-scoped object namespace. A trigger is excluded when either it or its parent object is excluded (a table's exclusion takes its triggers with it). Extended properties are one pass over `sys.extended_properties` (classes 0/1/2/3/6/7; class 1 restricted to the extracted object kinds, class 6 to table types) with the `(class, major_id, minor_id)` target resolved to names in SQL; a property follows its excluded owner (including a trigger's excluded parent), and `IgnoreExtendedProperties` skips the query entirely. Object exclusion comes from `ObjectNamesToIgnore` plus, when `IgnoreSysDiagramObjects` is set, the SSMS diagram object names (additive union) — this now actually excludes `fn_diagramobjects`, since functions are extracted. An ignore entry matches an object's bare name (any schema) or its schema-qualified `schema.name` (that schema only); the match set is built with `SchemaHashOptions.ObjectNameComparer` (default `OrdinalIgnoreCase`), so case behavior is owned by the library, not the caller's set. Schema filtering (`SchemaFilter` option) is applied in-memory after extraction.
- **`SchemaHashCalculator`** — `internal` (not part of the public API surface). Streams schema elements into `IncrementalHash` (SHA256). Each field is hashed in a fixed order, gated by the domain normalization enums; strings are length-prefixed and collections are count-prefixed to avoid boundary collisions. Elements are projected to their *effective* (post-normalization) values before being sorted and hashed, so option-equivalent databases sort and hash identically. `GetEffectiveIndex` applies the `IndexNormalization` bits (name/clustering/sort-order plus fill factor, pad index, lock options, disabled); `EffectiveConstraintName`/`EffectiveConstraint*` apply the `ConstraintNormalization` bits (name plus FK/CHECK disabled/trust/NOT-FOR-REPLICATION) to **both** the hash and the sort keys. `IndexNormalization.NormalizeClustering` normalizes only rowstore CLUSTERED/NONCLUSTERED placement (via `EffectiveTypeDesc`), preserving the columnstore distinction. `IndexNormalization.IgnoreSortOrder` drops the `IsDescendingKey` flag. For auto-generated names, `ConstraintNormalization.NormalizeAutoGeneratedNames` collapses a name when the authoritative catalog `IsSystemNamed` flag is set **or** the name matches the `IsAutoGeneratedName` shape (the flag is recorded at CREATE time from whether the statement supplied a name, so it flips to false when a system-named constraint is scripted out and recreated with its literal name — the shape check keeps such names normalized across that boundary); `IndexNormalization.NormalizeAutoGeneratedNames` (indexes have no such flag) uses only the `IsAutoGeneratedName` name-shape heuristic (`PK__Table__<hex>` and GUID-suffixed names). Column collation/ANSI-padding/masking, identity seed/NFR, temporal retention, and module SET options are likewise neutralized when their bits are set. The invariant: `…Normalization.Strict` (= 0) hashes with full fidelity, so an all-`Strict` options object reproduces the pre-enum hashes byte-for-byte.
- **`SchemaMetadata`** — Immutable record types that mirror the `sys.*` catalog one record per view: `TableSchema` (aggregate root; also carries `TemporalType`, `IsMemoryOptimized`/`DurabilityDesc`), `ColumnSchema` (catalog-named fields: `MaxLength`, `CollationName`, `ColumnId`, `EncryptionTypeDesc`, `XmlSchemaCollectionName`, `GeneratedAlwaysType`/`IsHidden`, …), `IndexSchema`/`IndexKeyColumn`, and the split constraint records `KeyConstraintSchema`/`ForeignKeyConstraintSchema`/`CheckConstraintSchema`/`DefaultConstraintSchema` (each carrying the authoritative `IsSystemNamed`). Also `ViewSchema` (definition hash + indexed-view `Indexes`; deliberately no columns — see its `<summary>`), `FunctionSchema` (`TypeDesc` distinguishes scalar/inline-TVF/multi-statement-TVF; a scalar function's return type is the `parameter_id = 0` row in `Parameters`), `TriggerSchema`/`TriggerEventSchema` (parent table/view, disabled/INSTEAD OF/NFR flags, DML event set with FIRST/LAST ordering), `SequenceSchema` (start/increment/bounds/cycle/cache — deliberately no `current_value`, which is runtime state), `SynonymSchema` (verbatim, unvalidated `BaseObjectName`), and `ExtendedPropertySchema` (`ClassDesc` plus nullable resolved target names `SchemaName`/`ObjectName`/`SubObjectName`, and the `sql_variant` value as `ValueType` + `Value` — both null only for a NULL value, keeping it distinct from an empty string). Catalog `object_id`/`schema_id` are resolved to names at extraction and never stored (they are non-deterministic across databases). All schema objects are schema-qualified (`[schema].[name]`).
- **`SchemaHashOptions`** — Comparison settings. Normalization is grouped into five `[Flags]` enums (in `SchemaNormalization.cs`), one per domain: `Tables` (`TableNormalization`: column order, identity seed, identity NFR, temporal retention), `Columns` (`ColumnNormalization`: collation, ANSI padding, dynamic data masking), `Indexes` (`IndexNormalization`: names, auto-gen names, clustering, sort order, fill factor, pad index, lock options, disabled), `Constraints` (`ConstraintNormalization`: names, auto-gen names, disabled, trust, NOT-FOR-REPLICATION), and `Modules` (`ModuleNormalization`: body text, SET options). Each enum: `Strict = 0` (full fidelity), individual loosening bits, and a `Structural` combo; every bit only ever removes a distinction. Set bits directly (`Indexes = IndexNormalization.IgnoreFillFactor | IndexNormalization.IgnoreLockOptions`) or take a whole-domain combo (`Indexes = IndexNormalization.Structural`); `IgnoreNames` wins over `NormalizeAutoGeneratedNames` within a domain. Static presets: `V1` (V2 + index sort order ignored), `V2` (recommended; `Default` is an alias), `Structural` (composes each domain's `Structural` combo: ignores index/constraint names, clustering, key sort order, table column order). The per-domain `Structural` combos are defined to reproduce the existing preset hashes — the newer physical/enforcement/collation bits are **not** folded into any preset yet (a future presets round decides that). Object *scoping* is separate: `SchemaFilter`, `ObjectNamesToIgnore`, `IgnoreSysDiagramObjects`, and `IgnoreExtendedProperties` (skips extended-property extraction entirely; no preset sets it). Bare `new SchemaHashOptions()` is the neutral everything-exact baseline (all domains `Strict`, nothing excluded).

## Code Style

- Function parameters, constructor arguments, and record definitions should always be on a single line. Do not wrap parameters onto multiple lines.
- Terminology: call the output a **hash**, not a "digest" ("digest" is too academic). Use "hash" in comments, docs, test messages, and identifiers — the public API is `SchemaHashResult.Hash` and the envelope is `<version>:<base64hash>`.

### Important Details

- `IndexSchema.TypeDesc` holds the raw `sys.indexes.type_desc` (e.g. `CLUSTERED`, `NONCLUSTERED COLUMNSTORE`). The `IndexNormalization.NormalizeClustering` bit controls whether rowstore placement is normalized to `X-CLUSTERED` for comparison (columnstore variants stay distinct).
- Module body hashing (stored procedures, views, functions, triggers) uses SQL Server's `HASHBYTES('SHA2_256', ...)` server-side rather than transferring module text; the server-capability probe (major version / `EngineEdition`) that decides between `HASHBYTES` and the `CHECKSUM` fallback runs once in `ExtractSchemaAsync` and is shared by all four module kinds.
- The hash output path: `SchemaHashCalculator` produces lowercase hex → `SqlSchemaHash` converts hex to bytes to base64, then wraps it in a versioned **envelope** `<version>:<base64hash>` (e.g. `2:dGhpcyBpc...`). The envelope is added only at the `SqlSchemaHash` facade boundary via the private `Envelope`/`ResolveHashFormatVersion` helpers; the calculator stays a pure hex-hash producer. `<version>` defaults to the assembly major (`ResolveHashFormatVersion` is the single swap point for a future `major → hashVersion` map). Parse/compare envelopes via `SchemaHashResult` (`Parse`/`TryParse`, and `Compare` → `Equal`/`Different`/`Incomparable`); `TryParse` returns false for legacy bare-base64 so old stored hashes read as `Incomparable`. The envelope carries no options fingerprint — comparing hashes computed with different `SchemaHashOptions` is a caller-discipline concern (a mismatch surfaces as `Different`, not a distinct signal).
- Dependencies: `Dapper` for queries, `Microsoft.Data.SqlClient` for SQL Server connectivity.
