# Full-Text Indexes/Catalogs

## Scope and environment note

This pass targeted `sys.fulltext_catalogs`, `sys.fulltext_indexes`, and `sys.fulltext_index_columns` against a live SQL Server 2025 (17.x, build `17.0.1000.7`, Enterprise Developer Edition, Linux container) instance, in a dedicated `audit_full_text` schema inside the shared `audit_db` database (the literal hyphenated name `audit_full-text` requested is not a legal unquoted T-SQL identifier for `CREATE SCHEMA`, so an underscore variant was substituted, purely a naming accommodation, no semantic difference).

**Important finding, stated up front:** this container reports `SELECT FULLTEXTSERVICEPROPERTY('IsFullTextInstalled')` = `0` and `sys.fulltext_languages` returns **zero rows** (no word-breaker/language resources registered, the `mssql-server-fts` package is not installed alongside the base engine). `CREATE FULLTEXT CATALOG` still succeeds as pure metadata, but every `CREATE FULLTEXT INDEX` attempt failed with:
```
Msg 7609, Level 17, State 5: Full-Text Search is not installed, or a full-text component cannot be loaded.
```
So the experimentation below is a hybrid: `sys.fulltext_catalogs` was populated and queried against **real, created objects**; `sys.fulltext_indexes` / `sys.fulltext_index_columns` could not be populated in this environment, but their **live column definitions were still captured from the running 2025 instance** (an empty result set still returns the current column list/order, see below), and cross-checked against Microsoft Learn. This itself is a real-world edge case worth documenting for a coverage audit: a database can legitimately have full-text *catalogs* without the engine being able to *build* a full-text *index*, and extraction code must not assume `CREATE FULLTEXT CATALOG` succeeding implies indexing will work.

## Catalog views involved

| View | Grain | Purpose |
|---|---|---|
| `sys.fulltext_catalogs` | one row per full-text catalog in the database | Catalog-level container: name, default flag, accent sensitivity, owner. |
| `sys.fulltext_indexes` | one row per full-text index (at most one per table/indexed view) | Index-level metadata: which catalog it belongs to, its key index, change-tracking mode, stoplist/property-list association, engine version. |
| `sys.fulltext_index_columns` | one row per column participating in a full-text index | Column-level: which columns, per-column language, type column (document filtering), statistical semantics flag. |
| `sys.fulltext_languages` | one row per installed word-breaker language (LCID → name) | Resolves the `language_id` LCID values used above. **Empty in this environment** (no language resources installed), confirming `IsFullTextInstalled = 0` is accurate, not just a stale flag. |
| `sys.fulltext_index_catalog_usages` | one row per (table, full-text-index, catalog) reference | A `(object_id, index_id, fulltext_catalog_id)` cross-reference; functionally redundant with the `fulltext_catalog_id` already exposed directly on `sys.fulltext_indexes`, likely retained mainly for compatibility/tooling that predates the current shape of `sys.fulltext_indexes`. Still present and queryable as of SQL Server 2025. |
| `sys.registered_search_property_lists` | one row per search property list | Resolves `sys.fulltext_indexes.property_list_id`; out of scope for this pass beyond noting the FK relationship. |

## `sys.fulltext_catalogs` — columns

| Column | Type | Relevant to schema-change detection? | Notes |
|---|---|---|---|
| `fulltext_catalog_id` | int | No (surrogate, not deterministic across databases) | Assigned starting at 5 for the first catalog created in a database and incrementing per creation (documented behavior; observed directly, a scratch catalog we created and dropped got id 5, our two retained catalogs got 6 and 7). Must not be hashed as-is. |
| `name` | sysname | **Yes** | Catalog name, unique per database. |
| `is_default` | bit | **Yes** | Whether this is the catalog used when `CREATE FULLTEXT INDEX` omits an explicit catalog. Only one catalog can be default at a time; changing it is a schema-relevant change. |
| `is_accent_sensitivity_on` | bit | **Yes** | Set via `CREATE FULLTEXT CATALOG ... WITH ACCENT_SENSITIVITY = ON|OFF`; defaults to the database collation's accent sensitivity if unspecified. Confirmed by direct experiment: our default catalog (no explicit setting) came back `1` (accent-sensitive, matching the default `SQL_Latin1_General_CP1_CI_AS`-style collation), our alt catalog (`WITH ACCENT_SENSITIVITY = OFF`) came back `0`. Changing this forces an index rebuild per docs. |
| `principal_id` | int | Debatable, schema-relevant if the library considers catalog *ownership* in scope, otherwise skip (analogous to how this repo already treats other object ownership) | Owner principal (settable via `AUTHORIZATION`); both our catalogs report the same owner (`dbo`, principal_id 1) since no explicit `AUTHORIZATION` differed. |
| `data_space_id`, `file_id`, `path` | int, int, nvarchar(260) | **No, excluded** | Microsoft Learn explicitly flags these three as **deprecated / scheduled for removal**: "a full-text catalog is a virtual object and does not belong to any filegroup" since SQL Server 2008; these columns are vestiges of the pre-2008 file-based catalog model. Observed as `NULL`/not meaningful in this instance. Do not hash. |
| `is_importing` | bit | Runtime/transient, **exclude** | Per Microsoft Learn: `0` = catalog is being imported, `1` = not being imported (note the value semantics are the inverse of what "is_importing" would suggest by name). Both freshly created catalogs in our test read `0`. This looks tied to attach/restore/mirroring workflows rather than a stable schema property; treat as non-deterministic runtime state, not a hash input. |

## `sys.fulltext_indexes` — columns (live column list captured from the 2025 instance; population blocked in this environment, see note above)

| Column | Type | Relevant to schema-change detection? | Notes |
|---|---|---|---|
| `object_id` | int | Key, not a hash value itself | The table/indexed view the index belongs to; resolve to schema-qualified name the same way this repo already resolves other `object_id`s, don't hash the raw id. |
| `unique_index_id` | int | **Yes (by identity of the referenced index, not the raw id)** | Points at the existing unique, single-column, non-nullable index used as the full-text key (`KEY INDEX` clause). Resolve to that index's identity (e.g. name) rather than hashing the raw `index_id`. Per docs, this must be a unique key index; SQL Server enforces exactly one full-text index per table/indexed view. |
| `index_version` | int | **Yes, but version-gated, see below** | **New in SQL Server 2025 (17.x)**; not present on earlier server versions. Value `1` = legacy ("version 1") word-breaker/filter binaries (the value assigned to every pre-existing index carried through an in-place upgrade from SQL Server ≤2022); `2` = new SQL Server 2025 binaries (default for newly created indexes, subject to the `FULLTEXT_INDEX_VERSION` database-scoped configuration). This is a genuine schema-relevant/environment-relevant distinction on 2025+, since a v1 index can behave/fail differently (word-breaking errors) than a v2 index with otherwise identical DDL. |
| `fulltext_catalog_id` | int | Indirect, resolve to catalog name | Which catalog owns this index; join to `sys.fulltext_catalogs.name`, don't hash the id. |
| `is_enabled` | bit | **Yes** | Whether the index is currently enabled for querying/population (`ALTER FULLTEXT INDEX ... ENABLE/DISABLE`), an explicit, deliberately-toggled schema property, not transient crawl state. |
| `change_tracking_state` / `change_tracking_state_desc` | char(1) / nvarchar(60) | **Yes** | Persisted mode: `M`/`MANUAL`, `A`/`AUTO` (default), `O`/`OFF`. This is the field the task asked about specifically. See the "NO POPULATION is not observable" edge case below. |
| `stoplist_id` | int | Indirect, resolve to stoplist identity | Associated stoplist (`OFF` / `SYSTEM` / named); a real schema-relevant association, but resolve to name, not raw id. |
| `property_list_id` | int | Indirect, resolve to property-list identity | `NULL` if none associated; otherwise join `sys.registered_search_property_lists`. Version-gated: `SEARCH PROPERTY LIST` clause requires **SQL Server 2012 (11.x)+**. |
| `data_space_id` | int | Likely not meaningful post-2008 for the same reason as the catalog-level columns | Filegroup placement of the index; given catalogs themselves stopped being filegroup-bound in 2008, treat with the same skepticism as the catalog's deprecated placement columns unless evidence shows it's still load-bearing. |
| `has_crawl_completed`, `crawl_type` / `crawl_type_desc`, `crawl_start_date`, `crawl_end_date`, `incremental_timestamp` | bit, char(1)/nvarchar, datetime, datetime, binary(8) | **No, runtime state, explicitly excluded per task instructions** | Population/crawl progress and history, changes on every population run regardless of DDL; must never feed a schema hash. |

## `sys.fulltext_index_columns` — columns (live column list captured from the 2025 instance)

| Column | Type | Relevant to schema-change detection? | Notes |
|---|---|---|---|
| `object_id` | int | Key, not hashed raw | Same table the parent full-text index belongs to. |
| `column_id` | int | Resolve to column name | Which base-table column participates; resolve via `sys.columns` the same way other column references in this repo are resolved, rather than hashing the ordinal. |
| `type_column_id` | int, nullable | **Yes** | Only populated when the indexed column is `varbinary(max)`/`image` and `TYPE COLUMN` was specified, points at the column (must be `char`/`nchar`/`varchar`/`nvarchar`) holding the document's file-extension for filter selection (e.g. `.docx`, `.pdf`). `NULL` when not applicable. In our design, `Attachments.FileData` used `TYPE COLUMN FileExtension`, which is exactly this pairing, a good "document filtering" edge case for the audit. |
| `language_id` | int | **Yes** | Per-column LCID for the word-breaker/stemmer used to index that column, this is the "language" the task called out, and it is **per-column, not per-index** (a single full-text index can mix languages across its columns). `0` = neutral language (used for the "language unknown/mixed" case; recommended by Microsoft docs when the column holds multilingual or unclassifiable text). |
| `statistical_semantics` | int (effectively boolean: 0/1) | **Yes, version-gated** | `1` = the column additionally participates in statistical (semantic) key-phrase/similarity indexing. Requires **SQL Server 2012 (11.x)+** (`STATISTICAL_SEMANTICS` clause / Semantic Search feature, which itself depends on Full-Text Search being installed). |

## Notable edge cases found by direct experimentation

1. **Catalog DDL succeeds without the FTS engine; index DDL does not.** `CREATE FULLTEXT CATALOG` completed and populated `sys.fulltext_catalogs` normally even though `FULLTEXTSERVICEPROPERTY('IsFullTextInstalled') = 0` and `sys.fulltext_languages` is empty on this container. The very next `CREATE FULLTEXT INDEX` on either test table failed immediately with `Msg 7609`. A schema-hasher that only checks "does `sys.fulltext_catalogs` have rows" as a proxy for "full-text is usable here" would be fooled, catalogs and indexes need to be probed independently.
2. **`NO POPULATION` is not itself an observable, persisted flag.** Per Microsoft Learn's `CREATE FULLTEXT INDEX` documentation, `CHANGE_TRACKING OFF, NO POPULATION` only suppresses the *initial* crawl at creation time; afterward `sys.fulltext_indexes.change_tracking_state` reports the same `'O'`/`OFF` as an index created with plain `CHANGE_TRACKING OFF` (which *does* auto-populate). The only observable difference is transient (`has_crawl_completed`, which is explicitly out of scope for hashing). This means "was this index created with `NO POPULATION`" is **not** a schema fact recoverable from the catalog views after the fact, worth calling out so nobody tries to reconstruct it.
3. **`is_importing`'s documented polarity is counter to its name** (`0` = *is* being imported, `1` = is *not*). Both freshly created catalogs in this test read `0`. Given the inversion and the fact it's about a transient DB-attach/mirroring operation, treat it as runtime state, not schema state, but flag the counter-intuitive polarity if it's ever consulted.
4. **Deprecated filegroup-era columns confirmed live.** `sys.fulltext_catalogs.data_space_id` / `file_id` / `path` are explicitly marked by Microsoft ("will be removed in a future release... don't use these columns in new development"), a holdover from pre-SQL Server 2008 when catalogs were physical, file-backed objects. `CREATE FULLTEXT CATALOG`'s `ON FILEGROUP` / `IN PATH` clauses are documented as no-ops since 2008.
5. **Per-column language and per-column semantic indexing, mixed within one index.** Our `Documents` table's full-text index deliberately mixed `Title`/`Body LANGUAGE 1033` (English, `Body` also `STATISTICAL_SEMANTICS`) with `Notes LANGUAGE 0` (neutral) on the same index, exercising the fact that `language_id` and `statistical_semantics` live on `sys.fulltext_index_columns`, not `sys.fulltext_indexes`, i.e. per-column granularity is real and must be captured per column, not assumed uniform across the index.
6. **`TYPE COLUMN` document-filtering pairing.** `Attachments.FileData VARBINARY(MAX)` paired with `TYPE COLUMN FileExtension` (a `varchar` column holding literal extensions like `.pdf`) is the documented shape for indexing opaque binary blobs by content type; the type-column relationship shows up as `sys.fulltext_index_columns.type_column_id` pointing at the extension column's `column_id`. This is a distinct edge case from ordinary text columns and worth a dedicated test fixture if/when this object type is implemented.
7. **Full-text catalog id numbering starts at 5**, confirmed both by direct experiment (a scratch catalog we created and dropped got id `5`; our two retained catalogs got `6` and `7`) and by Microsoft Learn ("Full-text catalog IDs start at 00005"). Reinforces that these ids are pure surrogates and must never be hashed directly.
8. **At most one full-text index per table/indexed view, but the key index and catalog are independently choosable**, and a table's normal (non-full-text) indexes are entirely separate from its full-text key index, the `unique_index_id` FK is the only link between `sys.fulltext_indexes` and `sys.indexes`.

## Version gating observed / documented

- **Full-Text Search catalog views themselves** (`sys.fulltext_catalogs`, `sys.fulltext_indexes` core columns, `sys.fulltext_index_columns`) predate this repo's SQL Server 2016 (13.x) floor by a wide margin (feature and its catalog views have existed since SQL Server 2005/2008-era catalog-view naming), no gating concern for the repo's minimum target version on the base columns.
- **`STATISTICAL_SEMANTICS` / `sys.fulltext_index_columns.statistical_semantics`** and **`SEARCH PROPERTY LIST` / `sys.fulltext_indexes.property_list_id`**: require **SQL Server 2012 (11.x) or later** (Semantic Search / Search Property Lists). Both are safely above this repo's SQL Server 2016 floor, so no extra gating needed for this repo specifically, but note both additionally require the Full-Text/Semantic-Search *feature* to be installed at the instance level, which as this pass demonstrated is not guaranteed even on a modern, fully-licensed Enterprise Edition instance.
- **`sys.fulltext_indexes.index_version`** is **new in SQL Server 2025 (17.x)** and does not exist as a column on earlier server versions. Querying it unconditionally against a SQL Server 2016–2022 target would fail (unknown column), this is a genuine version-gating hazard for any extraction code that reaches this column, since the repo's floor (2016) predates it by nearly a decade. On in-place upgrade to 2025, pre-existing indexes are stamped `index_version = 1` (legacy word-breaker/filter binaries, which SQL Server 2025 no longer ships); newly created/rebuilt indexes default to `index_version = 2` unless overridden by `ALTER DATABASE SCOPED CONFIGURATION SET FULLTEXT_INDEX_VERSION = 1`. A `index_version = 1` index can fail full-text queries/population entirely post-upgrade (`Msg 30010`/`Msg 30011` per Microsoft's SQL Server 2025 breaking-changes documentation) even though the DDL shape is unchanged, a subtle case where the *catalog metadata looks identical* but the *runtime behavior differs*, which is exactly the kind of nuance a "structural" normalization mode would need to decide whether to fold in or not.
- **Full-Text Search / Semantic Search installation is always an optional, separately-installed engine component** (on Windows, the "Full-Text and Semantic Extractions for Search" Setup feature; on Linux, the separate `mssql-server-fts` package), never assumed present just because the SQL Server edition/version supports it, confirmed directly in this pass by getting `IsFullTextInstalled = 0` on an Enterprise Developer Edition SQL Server 2025 instance.

## Coverage audit

- **Full-text catalogs not captured**: `sys.fulltext_catalogs` is not queried anywhere in `SchemaExtractor`, and `SchemaMetadata` has no corresponding record type. `name`, `is_default`, and `is_accent_sensitivity_on` are all schema-relevant per the blind doc and are entirely unobserved. Not documented as a deliberate exclusion anywhere in CLAUDE.md, BUGS.md's "Out-of-scope object kinds" entry, or `website/docs/what-gets-hashed.md`'s "Not yet captured" section. Filed in BUGS.md as "Full-text catalogs not captured".
- **Full-text indexes not captured**: `sys.fulltext_indexes` is not queried anywhere in `SchemaExtractor`; there is no corresponding record in `SchemaMetadata`. The index's catalog association, `KEY INDEX` (`unique_index_id`, resolved to identity), `is_enabled`, `change_tracking_state`/`change_tracking_state_desc`, stoplist (`stoplist_id`, resolved to identity), property list (`property_list_id`, resolved to identity), and, on SQL Server 2025+, `index_version`, are all schema-relevant per the blind doc and entirely unobserved. Filed in BUGS.md as "Full-text indexes not captured".
- **Full-text index columns not captured**: `sys.fulltext_index_columns` is not queried anywhere in `SchemaExtractor`. Which columns participate (`column_id`, resolved to name), per-column `language_id`, the `TYPE COLUMN` document-filtering pairing (`type_column_id`, resolved to name), and `statistical_semantics` are all schema-relevant per the blind doc and entirely unobserved. Filed in BUGS.md as "Full-text index columns not captured".

The following blind-doc findings were checked and are **not** gaps, correctly out of scope, runtime state, or not independently observable:

- `sys.fulltext_catalogs.fulltext_catalog_id`, `sys.fulltext_indexes.object_id`/`fulltext_catalog_id`, and `sys.fulltext_index_columns.object_id` are all raw catalog surrogates the blind doc itself says must be resolved to identity rather than hashed; that requirement is folded into the corresponding gap entries above rather than filed separately.
- `sys.fulltext_catalogs.data_space_id`/`file_id`/`path` are Microsoft-deprecated, filegroup-era vestiges the blind doc itself says not to hash; correctly excluded from the filed gaps.
- `sys.fulltext_catalogs.is_importing` and `sys.fulltext_indexes.has_crawl_completed`/`crawl_type`/`crawl_type_desc`/`crawl_start_date`/`crawl_end_date`/`incremental_timestamp` are transient runtime/crawl state per the blind doc itself (and per this project's established runtime-state exclusion policy, the same reasoning already applied to `sys.sequences.current_value`); correctly excluded from the filed gaps.
- `sys.fulltext_catalogs.principal_id` (catalog ownership) is not filed as its own gap: the blind doc itself calls it "debatable," and this project has an established position (see BUGS.md's "Synonym explicit ownership" and "Schema ownership" entries) that no object kind currently captures owner/`principal_id` state as a matter of general, not-yet-decided scope, so a full-text-specific instance would not add new information beyond that existing, broader gap.
- `sys.fulltext_indexes.data_space_id` is flagged by the blind doc itself as "likely not meaningful post-2008," the same reasoning as the catalog-level placement columns; not filed as a gap absent evidence it is load-bearing.
- Whether an index was created with `NO POPULATION` is, per the blind doc's own edge case #2, not recoverable from the catalog after creation at all (the only observable trace is the excluded, transient `has_crawl_completed`), so there is no catalog field to extract for this and it is not a gap.
- `sys.fulltext_languages` and `sys.fulltext_index_catalog_usages` are resolution/cross-reference views, not independent schema facts: language names are consumed as `sys.fulltext_index_columns.language_id` (covered by the "Full-text index columns not captured" gap above), and the catalog-usage view is explicitly noted by the blind doc as functionally redundant with `fulltext_indexes.fulltext_catalog_id`. `sys.registered_search_property_lists` is explicitly out of scope for this pass per the blind doc itself.
