# Indexes

## Catalog views

Two views together fully describe an index's structure:

- **`sys.indexes`** — one row per index (or heap) on a "tabular object" (table, view, or table-valued function). Table indexes and indexed-view indexes are exposed identically through this same view, keyed by `object_id` — a view's `object_id` (from `sys.views`) joins here exactly like a table's.
- **`sys.index_columns`** — one row per column participating in an index (key column, included column, or partitioning column), keyed by `(object_id, index_id)` joining back to `sys.indexes`.

Both were queried directly against objects created in a scratch `audit_indexes` schema on a live SQL Server 2025 (17.0.1000.7) container.

A `sys.indexes` row exists even for a **heap** (`index_id = 0`, `name IS NULL`, `type = 0`/`HEAP`) — confirmed by creating `OrderLines` with only a nonclustered PK (no clustered index). A schema-hash implementation must filter these out (`name IS NOT NULL` or `index_id <> 0`); they carry no structural information of their own.

## sys.indexes — relevant columns

| Column | Type | Relevant to schema identity? | Notes |
|---|---|---|---|
| `object_id` | int | Join key only | Non-deterministic across databases — resolve to schema-qualified object name, don't store raw. |
| `name` | sysname | Yes | NULL for the heap row. Unique only within the object. |
| `index_id` | int | No (ordinal, not identity) | 0=heap, 1=clustered, >1=nonclustered, in creation order — not a stable cross-database identity key; sort/compare by `name` instead. |
| `type` / `type_desc` | tinyint / nvarchar(60) | Yes | Observed on this instance: `0 HEAP`, `1 CLUSTERED`, `2 NONCLUSTERED`, `5 CLUSTERED COLUMNSTORE`, `6 NONCLUSTERED COLUMNSTORE`, `9 JSON` (new — see version gating below). Not exercised here but documented: `3 XML`, `4 SPATIAL`, `7 NONCLUSTERED HASH` (memory-optimized only, see `sys.hash_indexes`). |
| `is_unique` | bit | Yes | Always 0 for clustered columnstore per docs. |
| `data_space_id` | int | Yes, but overlaps with partitioning | Filegroup or partition scheme id; 0 for a TVF or in-memory index. Out of scope of this pass (partitioning is a separate audit topic) but note it exists on the index row. |
| `ignore_dup_key` | bit | Yes | IGNORE_DUP_KEY ON/OFF. |
| `is_primary_key` | bit | Yes | 1 when the index backs a PK constraint. **Verified edge case below**: distinguishes a PK-backed index from a plain unique index and from a UNIQUE-constraint-backed index. |
| `is_unique_constraint` | bit | Yes | 1 when the index backs a `UNIQUE` constraint (as opposed to a directly-created unique index). |
| `fill_factor` | tinyint | Yes | 0 = server default; >0 = explicit FILLFACTOR. Always 0 for clustered columnstore. |
| `is_padded` | bit | Yes | PAD_INDEX ON/OFF. |
| `is_disabled` | bit | Yes | Verified: `ALTER INDEX ... DISABLE` sets this; the index's column metadata (`sys.index_columns` rows) is retained even while disabled. |
| `is_hypothetical` | bit | Exclude | 1 for indexes created by tools such as the Database Engine Tuning Advisor / `DBCC AUTOPILOT`; these hold only column-level statistics, are not deployable schema, and should be filtered out of any hash (Microsoft's own example query filters `is_hypothetical = 0`). Not created live here (no supported direct DDL) — documented from Microsoft Learn. |
| `is_ignored_in_optimization` | bit | Exclude (query-optimizer state) | Not a structural/DDL property. |
| `allow_row_locks` / `allow_page_locks` | bit | Yes | Lock-escalation options; always 0 for clustered columnstore. |
| `has_filter` | bit | Yes | 1 iff `filter_definition` is non-null. |
| `filter_definition` | nvarchar(max) | Yes | The filtered-index predicate, canonicalized by the server (bracketed identifiers, parenthesized literals). Verified: `WHERE IsDeleted = 0` → `([IsDeleted]=(0))`; a compound predicate `WHERE Notes IS NOT NULL AND Status > 0` → `([Notes] IS NOT NULL AND [Status]>(0))`. NULL for a heap, a non-filtered index, or if the caller lacks permission on the table (a metadata-visibility gotcha, not an absence-of-filter signal). |
| `compression_delay` | int | Yes | Columnstore rowgroup compression delay in minutes. Verified: NULL for every rowstore index; **0** for a columnstore index with no explicit delay configured (not NULL) — a rowstore-vs-columnstore-aware comparer must not conflate "NULL" and "0" as both meaning "no delay" across the two families. |
| `suppress_dup_key_messages` | bit | Yes | SQL Server 2017+ (and Azure SQL DB). Verified present as 0 on this instance. |
| `auto_created` | bit | Exclude | 1 only for indexes created by Azure SQL Database's automatic tuning feature — that's tooling/runtime provenance, not user-authored schema. Verified 0 for every manually-created index here. |
| `optimize_for_sequential_key` | bit | Yes | SQL Server 2019+ last-page-insert optimization (OPTIMIZE_FOR_SEQUENTIAL_KEY). Verified present as 0. |

## sys.index_columns — relevant columns

| Column | Type | Relevant to schema identity? | Notes |
|---|---|---|---|
| `object_id`, `index_id` | int | Join keys | — |
| `index_column_id` | int | No (ordinal position in the DDL column list, already captured by `key_ordinal`/`is_included_column`) | Unique within `index_id`; not itself a semantic property. |
| `column_id` | int | Yes (resolve to column name) | 0 = the RID in a nonclustered index (not observed as a real row here; documented). |
| `key_ordinal` | tinyint | Yes | 1-based position among key columns. **0** for: a non-key (included) column, **and** for every column of an XML, spatial, columnstore, or JSON index — verified directly for both `NCCI_Orders_Cols` (columnstore) and `IX_JsonDocs_Doc` (JSON): all rows show `key_ordinal = 0`. |
| `partition_ordinal` | tinyint | Yes, but partitioning-scoped | 1-based ordinal among partitioning columns; 0 = not one. A clustered columnstore index can have at most one. Left at 0 in every object created here (no partition scheme in play). |
| `is_descending_key` | bit | Yes | Verified: explicit `DESC` → 1, explicit or default `ASC` → 0. Always 0 for a columnstore or hash index column (per docs; also observed here). |
| `is_included_column` | bit | Yes | 1 for an explicit `INCLUDE` column, **and** 1 for every column of a columnstore index (verified: all 5 columns of `NCCI_Orders_Cols` and `CCI_SalesFact` show `is_included_column = 1`, `key_ordinal = 0` — a columnstore index has no "key" concept, every column is effectively "included"). **Edge case verified**: a JSON index's column shows `is_included_column = 0` too — it isn't grouped into either the key or included family, it's just present with both ordinal columns at 0. Columns implicitly present because they're the clustering key are *not* listed in `sys.index_columns` at all; columns implicitly present because they're a partitioning column are listed with `is_included_column = 0`. |
| `column_store_order_ordinal` | tinyint | Yes | **SQL Server 2022 (16.x)+** (also Azure SQL DB/MI, Synapse). Verified live: creating a columnstore index with an explicit `ORDER (col1, col2)` clause populates a 1-based ordinal on the ordered columns and leaves it 0 on the rest — tested on both a clustered columnstore (`CCI_SalesFact_Ordered ORDER (SaleDate, ProductId)`) and a nonclustered columnstore (`NCCI_OrderLines_Ordered ORDER (ProductId, Qty)`). |
| `data_clustering_ordinal` | tinyint | Present but inert on this instance | Documented as **SQL Server 2025 (17.x)**, "0 = not a columnstore index & data clustering ordinal doesn't apply". Verified live: even on an *ordered* clustered columnstore index (`CCI_SalesFact_Ordered ORDER (SaleDate, ProductId)`), every row still shows `data_clustering_ordinal = 0` — this column did not light up for the ordinary `ORDER` clause in this build; it appears to gate a distinct, not-yet-exercised data-clustering feature rather than being an alias for `column_store_order_ordinal`. Worth a follow-up before depending on it. |

## Version gating (confirmed on this instance / documented on Microsoft Learn)

- **`sys.indexes.type` / `type_desc` value `9` / `JSON`** — new in **SQL Server 2025 (17.x)**. Verified live: `CREATE JSON INDEX ix ON t(jsoncol)` (requires a native `JSON` column, itself new in 2025) produces a `sys.indexes` row with `type = 9`. Creating it required `SET QUOTED_IDENTIFIER ON` and `SET ANSI_NULLS ON` in the session (same requirement as filtered indexes / indexed views / computed-column indexes — see edge case below).
- **`sys.index_columns.column_store_order_ordinal`** — Microsoft Learn documents this as **SQL Server 2022 (16.x)+** (Azure SQL DB/MI, Synapse Analytics, "Always up to date" Azure). Confirmed populated on this SQL Server 2025 instance.
- **`sys.index_columns.data_clustering_ordinal`** — Microsoft Learn documents this as **SQL Server 2025 (17.x)** only. Present on this instance but stayed 0 in every experiment (see edge case above).
- **`sys.indexes.compression_delay`, `suppress_dup_key_messages`** — columnstore compression delay is columnstore-era (2014+ columnstore, `compression_delay` column itself general availability alongside `suppress_dup_key_messages`/`optimize_for_sequential_key` era columns); Microsoft Learn footnotes `suppress_dup_key_messages` as **SQL Server 2017 (14.x)+** (also Azure SQL DB/MI) and `optimize_for_sequential_key` as **SQL Server 2019 (15.x)+** (also Azure SQL DB/MI).
- **`sys.indexes.auto_created`** — footnoted as **Azure SQL Database**-specific (automatic tuning); expect 0 always on box-product SQL Server.
- Everything else exercised (filtered predicates, `INCLUDE`, key `ASC`/`DESC`, `FILLFACTOR`/`PAD_INDEX`, disabled indexes, indexed views, rowstore vs. columnstore, unique vs. PK vs. UNIQUE-constraint-backed) is long-standing (SQL Server 2008 or earlier) and not gated relative to this library's documented SQL Server 2016 minimum.

## Notable edge cases found by direct experimentation

1. **Heap rows in `sys.indexes`.** A table with no clustered index still produces a `sys.indexes` row: `index_id = 0`, `name = NULL`, `type_desc = 'HEAP'`. Must be filtered out (`name IS NOT NULL`) or it will be miscounted as an index.
2. **Columnstore indexes have no "key" columns.** For both the clustered and nonclustered columnstore indexes created here, every participating column has `key_ordinal = 0` and `is_included_column = 1` — there is no key/include distinction at the catalog level, unlike a rowstore index where `INCLUDE` columns are a deliberate subset.
3. **JSON indexes (2025+) are neither keyed nor included.** `key_ordinal = 0` and `is_included_column = 0` simultaneously — a third, distinct shape from both rowstore and columnstore index columns.
4. **PK-backed vs. UNIQUE-constraint-backed vs. plain unique index are three distinguishable states**, verified side by side on the same table (`OrderLines`): `PK_OrderLines` → `is_unique=1, is_primary_key=1, is_unique_constraint=0`; `UQ_OrderLines_OrderId_ProductId` (a `UNIQUE` table constraint) → `is_unique=1, is_primary_key=0, is_unique_constraint=1`; a directly-created `CREATE UNIQUE NONCLUSTERED INDEX` → `is_unique=1, is_primary_key=0, is_unique_constraint=0`. A schema hasher that only looks at `sys.key_constraints`/`sys.foreign_keys` for constraints would miss that constraint-backed uniqueness is *also* fully observable (and re-derivable) from `sys.indexes` alone.
5. **`compression_delay` is NULL for rowstore, but 0 (not NULL) for columnstore with no delay set.** Confirmed on `NCCI_Orders_Cols`: value is `0`, not `NULL`, despite no `COMPRESSION_DELAY` option ever being specified. Treating "0" and "NULL" as equivalent "no delay" sentinels across both index families would be a bug — the domain of the column effectively differs by index type (`NULL` is only meaningful for columnstore; rowstore is always `NULL`).
6. **`SET ANSI_NULLS ON` / `SET QUOTED_IDENTIFIER ON` are session-level DDL prerequisites, not stored index metadata.** Attempting to create a filtered index, an index on a computed column, an indexed view's index, or a JSON index with either SET option OFF fails at creation time (`Msg 1934`). This is *not* observable in `sys.indexes` afterward (there's no "ANSI NULLS off" flag on the index) — it only matters at the moment of `CREATE INDEX`/`CREATE VIEW ... WITH SCHEMABINDING`, so it's a caveat for anyone scripting these objects, not a catalog column to hash.
7. **Filter-predicate canonicalization.** The server rewrites the filter expression into a normalized bracketed form regardless of how it was typed: `WHERE IsDeleted = 0` is stored as `([IsDeleted]=(0))`; a two-clause `WHERE Notes IS NOT NULL AND Status > 0` is stored as `([Notes] IS NOT NULL AND [Status]>(0))`. Comparing `filter_definition` text directly (rather than re-parsing) is therefore comparing SQL Server's own canonical form, which is good for determinism but means whitespace/clause-order variations in the *source* DDL don't survive round-trip — only the server's chosen phrasing does.
8. **Disabled indexes retain full column metadata.** `ALTER INDEX ... DISABLE` sets `is_disabled = 1` but the corresponding `sys.index_columns` rows are untouched — a disabled index is still fully describable/comparable, it just can't be used by the optimizer.
9. **Indexed views use the exact same two catalog views as table indexes**, keyed by the view's `object_id`. The mandatory first index (`CREATE UNIQUE CLUSTERED INDEX ... ON view`) shows up with `type_desc = 'CLUSTERED'`, `is_unique = 1`, but critically `is_primary_key = 0` and `is_unique_constraint = 0` — it's a plain unique clustered index, not a constraint, even though SQL Server requires it to exist and be unique+clustered before any other index can be added to that view.
10. **A table can carry at most one columnstore index (of either flavor) at a time.** Attempting to add a second (`CREATE NONCLUSTERED COLUMNSTORE INDEX` on a table that already had one) fails with `Msg 35339, Multiple columnstore indexes are not supported` — a rowstore clustered/nonclustered index can coexist with one columnstore index on the same table, but not two columnstore indexes together.
11. **`is_hypothetical` indexes are a documented exclusion, not one reproduced live here** — Microsoft's own reference query for `sys.indexes` filters `is_hypothetical = 0` before treating rows as real indexes, since hypothetical indexes (created by tuning tools) hold only column-level statistics and aren't deployable schema.
12. **Physical compression (`DATA_COMPRESSION = PAGE/ROW/COLUMNSTORE`) is not a `sys.indexes` column at all** — it lives in `sys.partitions.data_compression`/`data_compression_desc`, joined on `(object_id, index_id[, partition_number])`, even for a completely unpartitioned index (verified: a non-partitioned `PAGE`-compressed index still has exactly one `sys.partitions` row, `partition_number = 1`, carrying the compression setting). Any index-schema hash that ignores `sys.partitions` will silently miss compression-level schema drift.

## Runtime/state columns explicitly excluded from the above (not schema)

- `sys.indexes.is_ignored_in_optimization` — optimizer bookkeeping, not a persisted structural choice.
- `sys.indexes.is_hypothetical`, `auto_created` — tooling/automatic-tuning provenance, not user schema.
- Anything from `sys.dm_db_index_*` DMVs, `sys.partitions.rows`, page/row counts, fragmentation, or `sys.dm_db_index_usage_stats` — all live/runtime, out of scope by definition (not queried here, noted only to draw the boundary explicitly).
- `sys.indexes.index_id` itself is a creation-order ordinal, not a stable identity — safe to use for joining within one snapshot, unsafe as a cross-database comparison key (use `name`, schema-qualified to the owning table/view, instead).

## Setup used for this audit (for reproducibility)

Created in schema `audit_indexes` on the shared `sqlschemahasher-audit` SQL Server 2025 container: a heap-with-nonclustered-PK table (`OrderLines`) and a clustered-PK table (`Orders`) exercising plain/composite/`INCLUDE`/filtered/unique/fill-factor+pad/disabled/computed-column/lock-option nonclustered indexes plus a nonclustered columnstore index; a `SalesFact` table with a clustered columnstore index (plain, then rebuilt as an ordered `CCI ... ORDER(...)`); a schema-bound indexed view (`vw_OrderTotals`) with its mandatory unique clustered index plus a secondary nonclustered `INCLUDE` index; a table (`SysNamedPk`) with a system-named PK to inspect the auto-generated index-name shape (`PK__SysNamedPk__<hex>`); a `UNIQUE` table constraint (`OrderLines`) to compare against plain unique/PK-backed indexes; a `JsonDocs` table with a native `JSON` column and a `CREATE JSON INDEX` (SQL Server 2025 exclusive); and a page-compressed nonclustered index to exercise `sys.partitions.data_compression`.

## Coverage audit

- **`sys.indexes.compression_delay` not extracted or hashed**: `IndexSchema`/`SchemaExtractor`'s index query carries no `compression_delay` column, so two columnstore indexes differing only in their configured `COMPRESSION_DELAY` compare as identical. This is a real, always-present columnstore attribute (0 vs. NULL is meaningful per the blind doc), not runtime state, and is not covered by any existing BUGS.md entry.
- **`sys.indexes.suppress_dup_key_messages` and `optimize_for_sequential_key` not extracted or hashed**: unlike the index's other physical/behavioral options (`fill_factor`, `is_padded`, `allow_row_locks`, `allow_page_locks`, `ignore_dup_key`), these two are absent from both the extraction query and `SchemaHashCalculator.HashIndexes`.
- **`sys.index_columns.column_store_order_ordinal` (SQL Server 2022+) not extracted or hashed**: the extractor's index-columns query selects `key_ordinal`/`is_included_column`/`is_descending_key` but not `column_store_order_ordinal`. Because columnstore columns already hash with `key_ordinal` effectively 0 and are tie-broken by name, an `ORDER (...)`-clustered columnstore index and the same index without that clause (or with the columns in a different declared order) currently hash identically.
- **Index-level `DATA_COMPRESSION` (`sys.partitions.data_compression`) not captured**: neither `SchemaExtractor` nor `SchemaHashCalculator` reads `sys.partitions`. A completely unpartitioned index still carries exactly one `sys.partitions` row with its compression setting (per the blind doc's verified edge case #12), so this gap applies even outside of table partitioning and is not covered by the existing "Partitioning and filegroup/data-space placement" BUGS.md entry.

All other columns confirmed relevant by the blind doc (`name`, `type`/`type_desc`, `is_unique`, `ignore_dup_key`, `is_primary_key`, `is_unique_constraint`, `fill_factor`, `is_padded`, `is_disabled`, `allow_row_locks`/`allow_page_locks`, `filter_definition`, `column_id`, `key_ordinal`, `is_descending_key`, `is_included_column`) are extracted and hashed correctly, including the documented edge cases (heap-row filtering, `is_hypothetical` exclusion, columnstore key/include collapse, JSON-index neither-keyed-nor-included shape, and the PK-vs-UNIQUE-constraint-vs-plain-unique three-way distinction via `is_primary_key`/`is_unique_constraint`). `data_space_id` and `sys.index_columns.partition_ordinal` are correctly out of scope under the existing partitioning/filegroup exclusion. `data_clustering_ordinal` (SQL Server 2025) was not filed as a gap: it stayed 0 in every experiment in the blind doc, so its schema-identity relevance is unconfirmed pending a follow-up audit.
