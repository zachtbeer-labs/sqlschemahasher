# Stored Procedures

## Scope of this note

Findings below come from direct experimentation against a live SQL Server 2025 (17.0.1000.7) instance, cross-checked against Microsoft Learn. Test objects were created in schema `[audit_stored-procedures]`:

- `IdListType` — a user-defined table type (`Id INT PK`, `Label NVARCHAR(100)`), used only as the READONLY table-valued-parameter type for the procs below.
- `usp_UpsertWidget(@Name, @Quantity = 1, @Ids IdListType READONLY, @NewId OUTPUT, @Notes OUT)` — the "normal" case: input param, input param with a default, a READONLY TVP, and two OUTPUT params (one via `OUTPUT`, one via the `OUT` synonym).
- `usp_SecretLogic(@X) WITH ENCRYPTION` — the encrypted-body edge case.
- `usp_RecompileExecAs(@Y) WITH RECOMPILE, EXECUTE AS OWNER` — module-option edge case.

## Catalog views that expose stored procedures

| View | Role |
| --- | --- |
| `sys.objects` | Base/central catalog row. `type = 'P'` (`type_desc = 'SQL_STORED_PROCEDURE'`) for plain T-SQL procs, `type = 'PC'` (`CLR_STORED_PROCEDURE`) for CLR procs, `type = 'X'` (`EXTENDED_STORED_PROCEDURE`, legacy xp_* DLLs, deprecated). Carries `name`, `schema_id`, `create_date`, `modify_date`, `is_ms_shipped`, `principal_id` (non-null only when ownership was reassigned away from the schema owner via `ALTER AUTHORIZATION`). |
| `sys.procedures` | A view derived from `sys.objects` (same `object_id`), adding proc-specific replication/startup flags: `is_auto_executed`, `is_execution_replicated`, `is_repl_serializable_only`, `skips_repl_constraints`. All four were `0` on my plain procs (no replication configured), so I could not force non-default values experimentally, but they are schema-relevant when replication *is* configured. |
| `sys.parameters` | One row per parameter, keyed by `object_id` + `parameter_id`, shared with functions (same view backs both). |
| `sys.sql_modules` | One row per module (proc/view/function/trigger), keyed by `object_id`, holding the definition text and the SET-option/compile flags recorded at CREATE time. |
| `sys.numbered_procedures` / `sys.numbered_procedure_parameters` | Legacy "numbered procedures" (`proc;2`, `proc;3`, ...). **Deprecated** and not present in Azure SQL Database at all (per Microsoft Learn's "Applies to" list — SQL Server, Managed Instance, Synapse, PDW, Fabric, but not Azure SQL DB). I did not create a numbered procedure (the feature fires a `DEPRECATION_ANNOUNCEMENT` event on use and Microsoft's docs recommend against it), but it is a real historical shape worth being aware of: a base object's own parameters live in `sys.parameters` as normal, while numbers ≥2 have *their own* parameter rows only in `sys.numbered_procedure_parameters`, keyed by `(object_id, procedure_number)`.

`sys.objects` and `sys.procedures` share the same `object_id`; join on that to combine base metadata with the proc-specific flags.

## Fields relevant to schema-change detection

### From `sys.objects` / `sys.procedures`

- `name`, `schema_id` (resolve to schema name) — identity.
- `type` / `type_desc` — distinguishes T-SQL (`P`) from CLR (`PC`) from extended (`X`) procedures; a schema-change detector should probably branch or explicitly exclude the CLR/extended kinds since their "body" isn't T-SQL text.
- `is_auto_executed`, `is_execution_replicated`, `is_repl_serializable_only`, `skips_repl_constraints` — genuine schema-relevant flags (replication behavior), not runtime state.
- **Explicitly runtime/non-deterministic, exclude from a hash**: `object_id` (per-database, reassigned on drop+recreate — confirmed: `ALTER PROCEDURE` preserves `object_id`/`create_date` and only bumps `modify_date`, but a `DROP`+`CREATE` gets a brand-new `object_id`), `create_date`, `modify_date` (these are wall-clock, will differ across environments even with byte-identical procedures), `principal_id` (individual ownership override — arguably schema-relevant if you care about permissions, but it's identity/security state, not "shape").

### From `sys.parameters`

- `name`, `parameter_id` (ordinal position — order matters, it's part of the calling contract), `system_type_id`, `user_type_id` (resolve via `sys.types`/`sys.table_types` to a name), `max_length`, `precision`, `scale`, `is_output`, `is_readonly` (READONLY table-valued parameter marker), `is_nullable`, `is_cursor_ref`, `xml_collection_id` (XML schema binding for typed-XML params), `encryption_type`/`encryption_type_desc`/`encryption_algorithm_name`/`column_encryption_key_id` (Always Encrypted parameterization metadata, SQL Server 2016+).
- **`vector_dimensions` / `vector_base_type` / `vector_base_type_desc`** — new in **SQL Server 2025 (17.x)** for the `vector` parameter type. Version-gated; will be absent/irrelevant pre-2025.
- **Confirmed footgun — `has_default_value` / `default_value` are useless for T-SQL procedures.** I declared `@Quantity INT = 1` and `@Notes VARCHAR(MAX) = NULL OUT` and queried `sys.parameters`:

  ```
  pname       has_default_value   default_value
  @Name       0                   NULL
  @Quantity   0                   NULL   <- has a real default of 1, not reflected here
  @Ids        0                   NULL
  @NewId      0                   NULL
  @Notes      0                   NULL   <- has a real default of NULL, not reflected here
  ```

  Microsoft Learn confirms this is by design, not a bug: *"SQL Server only maintains default values for CLR objects in this catalog view; therefore, this column has a value of 0 for Transact-SQL objects. To view the default value of a parameter in a Transact-SQL object, query the `definition` column of `sys.sql_modules`, or use `OBJECT_DEFINITION`."* **Any change-detection approach that wants to notice "the default value of `@Quantity` changed from 1 to 5" for an ordinary T-SQL procedure must parse it out of the module definition text (or rely on the definition-text hash catching the change incidentally) — it cannot read it structurally off `sys.parameters`.**
- `system_type_id = 243` is the generic "table type" marker for a table-valued parameter; it does **not** by itself identify *which* table type. Confirmed: `@Ids` has `system_type_id = 243`, `user_type_id = 258`; joining `user_type_id` to `sys.table_types` resolves it to `type_table_object_id = 1063674837` / name `IdListType`. Two procedures each taking *different* TVP types would both show `system_type_id = 243` — the actual type identity comes only from resolving `user_type_id`, schema-qualified.
- `is_readonly = 1` confirms the TVP is `READONLY` (mandatory for all table-valued parameters — SQL Server won't let you declare one without it).
- The TVP parameter row does **not** carry its target type's own column/constraint shape — that lives in `sys.table_types` + `sys.columns` (keyed by `type_table_object_id`), a separate object-type concern.

### From `sys.sql_modules`

- `definition` — the module's T-SQL source text. **`NULL` when the module was created `WITH ENCRYPTION`** — confirmed: `usp_SecretLogic`'s `definition` is `NULL`, `OBJECTPROPERTY(object_id, 'IsEncrypted') = 1`, while the two non-encrypted procs both return their full text and `IsEncrypted = 0`.
- `uses_ansi_nulls`, `uses_quoted_identifier` — the `SET ANSI_NULLS`/`SET QUOTED_IDENTIFIER` session options **in effect at CREATE time**, baked into the module's metadata permanently. **Confirmed environmental gotcha**: all three of my procedures came back `uses_quoted_identifier = 0` even though `uses_ansi_nulls = 1`, purely because `sqlcmd`'s default session settings differ from, e.g., SSMS (which defaults `QUOTED_IDENTIFIER ON`). This means **byte-identical `CREATE PROCEDURE` text can produce different `sys.sql_modules` metadata depending on the client/tool used to run it** — a real source of "false positive" schema drift if these flags are hashed without normalization, and conversely a real source of missed drift if they're ignored entirely when they do matter (they affect NULL-comparison/quoting semantics at execution time).
- `is_schema_bound` — always `0` for a plain stored procedure (`SCHEMABINDING` isn't a valid option for `CREATE PROCEDURE`; it applies to views/functions). Per Microsoft Learn, this column is instead forced to `1` for *natively compiled* stored procedures specifically (a different, unrelated reason for the bit being set).
- `is_recompiled` — `1` iff created `WITH RECOMPILE`. Confirmed on `usp_RecompileExecAs` (`is_recompiled = 1`), `0` on the other two.
- `execute_as_principal_id` — `NULL` by default / for `EXECUTE AS CALLER`; the target's `principal_id` for `EXECUTE AS SELF`/`EXECUTE AS <principal>`; the sentinel `-2` for `EXECUTE AS OWNER`. Confirmed: `usp_RecompileExecAs` (`EXECUTE AS OWNER`) shows `-2`; the other two (no `EXECUTE AS` clause, so implicit `CALLER`) show `NULL`.
- `uses_native_compilation` — `1` for natively compiled procedures (In-Memory OLTP, SQL Server 2014+); `0` for all mine (none were natively compiled — that requires a memory-optimized filegroup, not set up in this container).
- `null_on_null_input`, `uses_database_collation` — relevant mainly to scalar functions, always benign/`0` for ordinary procedures but present on the same view.
- `is_inlineable` / `inline_type` / `inline_eligibility_mask` (SQL Server 2019+) — relevant to scalar UDF inlining, not to procedures as such, but they live on this same shared view; a procedure row will just carry `0`.

### Cross-check via `OBJECTPROPERTY`/`OBJECTPROPERTYEX`

These built-in functions surface the same facts as `sys.sql_modules` under different names and can be used as a secondary source or sanity check: `IsEncrypted`, `ExecIsAnsiNullsOn`, `ExecIsQuotedIdentOn`, `ExecIsWithNativeCompilation`, `ExecIsStartup`. I confirmed they agree exactly with the `sys.sql_modules` values above for all three test procedures.

## Body/definition hashing — HASHBYTES vs. fallback

`HASHBYTES('SHA2_256', sys.sql_modules.definition)` is the natural way to fingerprint a procedure body server-side (avoids transferring potentially large text just to diff it client-side). Experimentally confirmed and cross-checked:

- `HASHBYTES('SHA2_256', ...)` on the two plain procedures returned a stable 32-byte SHA-256 hex value each; **on the encrypted procedure it returned `NULL`** (because `definition` itself is `NULL` for an encrypted module — `HASHBYTES(NULL) = NULL`). **This means an encrypted procedure's body is invisible to any hash-of-`definition` approach: two `WITH ENCRYPTION` procedures with completely different (obfuscated) bodies are indistinguishable by this method — both hash to `NULL`.** A robust detector needs a separate signal for "this module is encrypted, body comparison is not possible" (e.g. `OBJECTPROPERTY(..., 'IsEncrypted')` or `sys.sql_modules.definition IS NULL`) rather than silently treating a `NULL` hash as "unchanged" or as a legitimate comparable value.
- `CHECKSUM(definition)` "works" on `NULL` input too, but not usefully: `CHECKSUM(NULL)` returns the documented sentinel `2147483647` — confirmed experimentally. So a `CHECKSUM`-based fallback has the *same* blind spot as `HASHBYTES` for encrypted modules (every encrypted proc's checksum collapses to the same sentinel), on top of `CHECKSUM`'s already-weak collision guarantees (Microsoft Learn: it trims trailing whitespace and specifically ignores the `-` character in `nchar`/`nvarchar` input, so e.g. commented-out code or literal `-` vs. `N'-'` differences can be silently missed).
- **Version gating for `HASHBYTES`** (per Microsoft Learn): `SHA2_256`/`SHA2_512` require SQL Server **2012 (11.x)+**; all older algorithms (`MD2`/`MD4`/`MD5`/`SHA`/`SHA1`) are deprecated as of **2016 (13.x)**. Separately, **"For SQL Server 2014 (12.x) and earlier, allowed input values are limited to 8000 bytes"** — a large procedure body (multi-KB T-SQL) could silently be truncated/rejected on those older engines. Since this project's documented minimum server is SQL Server 2016, the 8000-byte input cap should never bite in practice for on-prem/Azure SQL DB — but the "major version / EngineEdition" style probe such an implementation would need is a real, documented distinction, not a hypothetical one: `HASHBYTES`'s "Applies to" list differs across SQL Server / Azure SQL Database / Azure SQL Managed Instance / Azure Synapse Analytics / Analytics Platform System, and those editions have historically diverged on which algorithms and input sizes are supported — so probing `SERVERPROPERTY('EngineEdition')`/`ProductMajorVersion` before choosing `HASHBYTES` vs. a `CHECKSUM`/`BINARY_CHECKSUM` fallback is the documented-safe approach rather than assuming uniform behavior across all "SQL Server-family" targets.
- Practical implication for a hashing library: prefer `HASHBYTES('SHA2_256', definition)` when `definition IS NOT NULL`; treat `definition IS NULL` (encrypted module) as its own explicit state in the hash rather than passing the NULL through to `HASHBYTES`/`CHECKSUM`, since both silently collapse to a single indistinguishable value for *all* encrypted bodies.

## Notable edge cases found by direct experimentation

1. **`has_default_value`/`default_value` in `sys.parameters` are always `0`/`NULL` for ordinary T-SQL procedures**, regardless of whether the parameter actually has a default (documented Microsoft behavior, confirmed above). Default values must be recovered from the definition text.
2. **`WITH ENCRYPTION` nulls out `sys.sql_modules.definition`** entirely (confirmed), and consequently nulls out any hash computed directly from it. `OBJECTPROPERTY(object_id, 'IsEncrypted')` (or checking `definition IS NULL` alongside `is_ms_shipped = 0`) is the reliable signal that body comparison isn't possible for that object.
3. **`ALTER PROCEDURE` preserves `object_id` and `create_date`, only bumping `modify_date`**; a `DROP`+`CREATE` on the other hand mints a brand-new `object_id`. Neither `create_date`/`modify_date`/`object_id` should feed a content hash — they reflect deployment history, not schema shape, and two environments with byte-identical procedures will disagree on all three.
4. **`uses_quoted_identifier` (and by extension `uses_ansi_nulls`) is captured from the client session at `CREATE`/`ALTER` time**, not derived from the script text alone — I got `uses_quoted_identifier = 0` from every procedure I created via `sqlcmd` (its default differs from SSMS's default of `ON`). Two teams deploying the *identical* `CREATE PROCEDURE` script through different tools/session settings can end up with different `sys.sql_modules` metadata for otherwise-identical procedures — a real source of noise (or, if intentionally tracked, a real source of signal) for a schema-hash.
5. **A READONLY table-valued parameter's row in `sys.parameters` carries only a type reference** (`system_type_id = 243` is a generic "this is *some* table type" marker; `user_type_id` must be resolved via `sys.table_types`/`sys.types` to learn *which* type, e.g. `IdListType`). The type's own column/constraint definition is a separate object graph, not part of the procedure's parameter row.
6. **`CHECKSUM(NULL)` is not "no signal," it's a specific fixed value (`2147483647`)** — documented and confirmed. A checksum-based fallback for encrypted-module bodies has the exact same "all NULLs collide" blind spot as `HASHBYTES`.
7. **Numbered procedures (`proc;2`, `proc;3`, ...) are a deprecated, Azure-SQL-DB-unsupported shape** with their own catalog views (`sys.numbered_procedures`, `sys.numbered_procedure_parameters`) that only cover procedure numbers ≥2 — the base procedure's own row/parameters live in the normal `sys.objects`/`sys.procedures`/`sys.parameters` views. A comprehensive extractor targeting on-prem SQL Server would need to know this shape exists even though it's discouraged.

## Version gating observed / documented

- **Minimum useful baseline for this object type is SQL Server 2016 (13.x)**: Always Encrypted parameter metadata (`encryption_type`, `encryption_type_desc`, `encryption_algorithm_name`, `column_encryption_key_id`, `column_encryption_key_database_name` on `sys.parameters`) is gated to 2016+.
- **SQL Server 2025 (17.x)** adds `vector_dimensions`, `vector_base_type`, `vector_base_type_desc` to `sys.parameters` for the new `vector` data type — confirmed present as columns on this 17.0 instance's catalog (not exercised experimentally since it's outside this object type's normal shape, but real and version-gated).
- **`is_inlineable`/`inline_type`** on `sys.sql_modules` are gated to SQL Server 2019 (15.x)+; `inline_eligibility_mask` is Fabric-only (SQL analytics endpoint / Warehouse), not applicable to on-prem SQL Server at all.
- **`uses_native_compilation`** on `sys.sql_modules` is gated to SQL Server 2014 (12.x)+.
- **`HASHBYTES`**: `SHA2_256`/`SHA2_512` need 2012 (11.x)+; unlimited (>8000 byte) input needs 2016 (13.x)+ — matches this project's documented minimum-supported-server line exactly, so the 8000-byte cap is a non-issue for in-scope servers but is the real, documented reason a version/edition probe before choosing a hash strategy is warranted.
- **Numbered procedures** (`sys.numbered_procedures`/`sys.numbered_procedure_parameters`): supported on SQL Server (on-prem), Azure SQL Managed Instance, Azure Synapse Analytics, Analytics Platform System, and Fabric warehouse/endpoint — explicitly **not listed for Azure SQL Database**, and deprecated everywhere it does exist.

## Coverage audit

- **Stored procedure `WITH RECOMPILE` not captured**: `sys.sql_modules.is_recompiled` is not extracted or hashed. `StoredProcedureSchema` (`src/SchemaMetadata.cs`) has no corresponding field, and `SchemaExtractor.ExtractStoredProceduresAsync`'s query does not select `m.is_recompiled`. Confirmed by the blind doc's own experiment (`usp_RecompileExecAs` → `is_recompiled = 1`). Not documented as a deliberate exclusion anywhere in BUGS.md or `website/docs/what-gets-hashed.md`.
- **Stored procedure `EXECUTE AS` context not captured**: `sys.sql_modules.execute_as_principal_id` is not extracted or hashed for procedures. `StoredProcedureSchema` has no corresponding field. BUGS.md already documents this exact gap for *triggers* ("Trigger `EXECUTE AS` context not captured") but the equivalent for stored procedures was not previously filed — the extractor's proc query does not select `m.execute_as_principal_id` at all. Confirmed by the blind doc (`usp_RecompileExecAs` with `EXECUTE AS OWNER` → `-2`).
- **Stored procedure native compilation not captured**: `sys.sql_modules.uses_native_compilation` is not extracted or hashed for procedures (`is_schema_bound`, the derived/forced flag for the same feature, is likewise absent, but per the blind doc carries no independent information for procedures). Neither field appears in `StoredProcedureSchema` or the extraction query.
- **Stored procedure replication/startup flags not captured**: `sys.procedures.is_auto_executed`, `is_execution_replicated`, `is_repl_serializable_only`, and `skips_repl_constraints` are not extracted or hashed — `SchemaExtractor.ExtractStoredProceduresAsync`'s query joins only `sys.procedures` for `SCHEMA_NAME`/`name` and `sys.sql_modules` for body/SET-option/recompile/execute-as fields; none of the four `sys.procedures`-specific columns are selected, and `StoredProcedureSchema` has no corresponding fields.
- **Stored procedure parameter Always Encrypted metadata not captured**: `sys.parameters.encryption_type`/`encryption_type_desc`/`encryption_algorithm_name`/`column_encryption_key_id` are not selected in `SchemaExtractor.ExtractParametersAsync`'s query, and `ParameterSchema` has no corresponding field — unlike `ColumnSchema.EncryptionTypeDesc`, which is already captured for table columns via `c.encryption_type_desc` in the columns query. This is a real asymmetry: the same Always Encrypted concept is tracked for columns but not for procedure/function parameters.
- **Numbered stored procedures not captured**: `sys.numbered_procedures`/`sys.numbered_procedure_parameters` are not queried anywhere in `SchemaExtractor`. A numbered procedure beyond `;1` is entirely invisible to extraction. Deprecated and Azure-SQL-DB-unsupported, but a real, queryable, on-prem shape per Microsoft Learn.

All other fields confirmed relevant by the blind doc — `name`/`schema_id` identity, `type = 'P'` filtering (CLR `PC`/extended `X` procedures are already excluded by the extraction query's `WHERE p.type = 'P'`), parameter `name`/ordinal position (preserved via extraction order)/resolved type name (including TVP `user_type_id` resolution to a schema-qualified table-type name)/`max_length`/`precision`/`scale`/`is_output`/`is_readonly`/`is_nullable`/`xml_collection_id` (resolved to a schema-qualified XML schema collection name)/`is_xml_document`, the encrypted-body `<encrypted>` sentinel, and `uses_ansi_nulls`/`uses_quoted_identifier` — are extracted and hashed correctly in `SchemaExtractor.ExtractStoredProceduresAsync`/`ExtractParametersAsync` and `SchemaHashCalculator.HashStoredProcedure`/`HashParameter`. `object_id`/`create_date`/`modify_date`/`principal_id` are correctly excluded as runtime/identity state, matching the blind doc's own guidance. `has_default_value`/`default_value` are correctly left uncaptured — the blind doc confirms these catalog columns are always `0`/`NULL` for T-SQL procedures regardless of an actual default, so there is nothing structural to extract; a default-value change is caught indirectly via the definition hash. CLR (`PC`) and extended (`X`) procedures, and the SQL-2025-only `vector_dimensions`/`vector_base_type`/`vector_base_type_desc` parameter columns, are out of scope per CLAUDE.md's documented scope statement.
