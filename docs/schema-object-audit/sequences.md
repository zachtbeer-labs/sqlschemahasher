# Sequences

## Catalog view(s)

- **`sys.sequences`** is the single catalog view exposing SQL Server sequence objects. It is a "base + extension" view: it inherits the common object columns (`name`, `object_id`, `schema_id`, `principal_id`, `parent_object_id`, `type`/`type_desc`, `create_date`, `modify_date`, `is_ms_shipped`, `is_published`, `is_schema_published`) from `sys.objects`, and adds sequence-specific columns. `type_desc = 'SEQUENCE_OBJECT'` (`type = 'SO'`).
- No second catalog view is needed to reconstruct a sequence's definition — unlike tables/views/procs, a sequence has no separate "definition text" or child rows (no columns, no parameters, no dependent index/constraint views). Everything schema-relevant is on the one row in `sys.sequences`.
- Extended properties on a sequence (if ever added) would come from `sys.extended_properties` with `class_desc = 'OBJECT_OR_COLUMN'` and `minor_id = 0`, keyed by the sequence's `object_id` — not tested here since it's out of scope for this pass, but noted for completeness since the object participates in the general object/schema extended-property namespace.

## Schema-relevant columns (from `sys.sequences`, cross-checked against Microsoft Learn)

| Column | Type | Meaning | Schema-relevant? |
|---|---|---|---|
| `name`, `schema_id` (→ schema name) | | Identity of the sequence, `[schema].[name]` | Yes |
| `system_type_id` | tinyint | System type id of the sequence's data type (e.g. `int`=56, `bigint`=127, `smallint`=52, `tinyint`=48, `decimal`=106) | Yes — data type of generated values |
| `user_type_id` | int | User-facing type id; for a plain built-in type this equals `system_type_id`, but for a sequence declared `AS <alias/UDT>` it resolves (via `sys.types.user_type_id`) to the alias type's own name, not the underlying built-in name. **Detecting a schema change correctly requires resolving `user_type_id`, not `system_type_id`** — a sequence built on a user-defined alias type reports the *alias* name here. | Yes |
| `precision`, `scale` | tinyint | Precision/scale of the type. `scale` is documented as "always 0 for sequence objects because only integer types are allowed" — confirmed: `decimal`/`numeric` sequences are only legal at scale 0 (see edge case below). | Yes (precision varies by declared type; scale is always 0 in practice) |
| `start_value` | sql_variant | The value the sequence (re)starts at. **Not immutable** — `ALTER SEQUENCE ... RESTART WITH <n>` permanently overwrites this column (see edge case below), so it is a genuine, ALTER-able schema property, not merely a "creation-time constant." | Yes |
| `increment` | sql_variant | Step size (negative ⇒ descending sequence). Cannot be 0. | Yes |
| `minimum_value` / `maximum_value` | sql_variant (nullable) | Effective bounds. If `MINVALUE`/`MAXVALUE` was omitted at create/alter time, these are back-filled with the data type's own min/max (e.g. omitting both on an `INT` sequence yields `-2147483648`/`2147483647`) — the column is never actually NULL in practice for a created sequence, it just reflects the type default. | Yes |
| `is_cycling` | bit | Whether the sequence wraps at the bound (`CYCLE`) or errors (`NO CYCLE`, the default) | Yes |
| `is_cached` | bit | `0` = created `NO CACHE`; `1` = caching enabled (default `CACHE` with an engine-chosen size) | Yes |
| `cache_size` | int (nullable) | Explicit cache size if one was specified (e.g. `CACHE 50` → `50`). **NULL both when `NO CACHE` was specified AND when `CACHE` was specified without a number** (engine picks an internal default) — these two NULL-producing cases are only distinguishable via `is_cached` (0 vs 1), not `cache_size` alone. Per Microsoft Learn, the engine-chosen default size is explicitly *not* guaranteed stable across versions/patches, so a hash calculator should probably treat "default cache" (`is_cached=1, cache_size=NULL`) as one equivalence class rather than trying to predict a concrete number. | Yes (as an `(is_cached, cache_size)` pair) |

## Explicitly excluded — runtime state, not schema

| Column | Why it's runtime state |
|---|---|
| `current_value` | The last value actually handed out by `NEXT VALUE FOR` (or `sp_sequence_get_range`) — mutates on every consumption, with no DDL involved. Two databases created from byte-identical `CREATE SEQUENCE` scripts diverge in `current_value` the moment either one is queried by an application. Hashing it would make the "schema hash" non-deterministic and dependent on application traffic, defeating the purpose of a schema hash. Confirmed experimentally: calling `NEXT VALUE FOR` three times against `Seq_Basic` moved `current_value` from `1`→`3` while every other catalog column stayed byte-identical. |
| `is_exhausted` | Derived, transient flag — becomes `1` purely as a side effect of consumption reaching the bound on a `NO CYCLE` sequence. Confirmed experimentally: advancing `Seq_NoCycle_AtMax` (tinyint, `MAXVALUE 255`) to `current_value = 255` flipped `is_exhausted` to `1` with no DDL executed; a subsequent `ALTER SEQUENCE ... RESTART WITH 10` flipped it straight back to `0`. Two databases with the identical `CREATE SEQUENCE` statement can disagree on this bit purely based on how many times each has been called. |
| `last_used_value` | Also last-consumed-value bookkeeping (feeds `sp_sequence_get_range` / diagnostics), same non-determinism as `current_value`. **Version-gated**: per Microsoft Learn, this column "applies to SQL Server 2017 and later" — the project's documented minimum supported server is SQL Server 2016 (13.x), so a naive `SELECT *` from `sys.sequences` that includes this column would need to tolerate its absence/behavior on the oldest supported server (worth explicit verification against a real 2016 instance; this was cross-checked against docs only, not tested live, since the shared container is SQL Server 2025). |
| `create_date`, `modify_date` | Wall-clock timestamps of DDL operations — vary by when the DDL ran, not by what the DDL produced. Standard "catalog metadata, not schema content" exclusion, consistent with how the rest of this codebase treats `object_id`/timestamps. |
| `object_id`, `schema_id`, `principal_id` (raw ids) | Non-deterministic across databases (assigned by the engine); only their *resolved names* (`name`, schema name, resolved owner name if ever surfaced) are schema-relevant, same pattern as every other object type in this library. |

## Edge cases found by direct experimentation

1. **`decimal`/`numeric` sequences require scale 0.** `CREATE SEQUENCE ... AS DECIMAL(5,2) ...` fails with error 11702: *"The sequence object ... must be of data type int, bigint, smallint, tinyint, or decimal or numeric with a scale of 0..."* Only `DECIMAL(p,0)` is legal. This matches the documented `sys.sequences.scale` remark ("Scale is always 0 for sequence objects because only integer types are allowed") — the catalog column isn't just reporting a fact, it's reporting an *enforced invariant*.
2. **`ALTER SEQUENCE ... RESTART WITH <n>` mutates `start_value` in the catalog, not just `current_value`.** This was the most surprising find. After `CREATE SEQUENCE ... START WITH 250 ...` and consuming values up to 255 (triggering `is_exhausted = 1`), running `ALTER SEQUENCE ... RESTART WITH 10` set **both** `current_value` and `start_value` to `10` in `sys.sequences`, and reset `is_exhausted` to `0` and `last_used_value` to `NULL`. A subsequent **plain** `ALTER SEQUENCE ... RESTART` (no `WITH`) then resumed from `10`, not the original `250`. This nuances the Microsoft Learn wording for plain `RESTART` ("the sequence numbering restarts based on the original CREATE SEQUENCE options") — in practice it restarts from the *current* `start_value`, which a prior `RESTART WITH` can have permanently overwritten. Practical implication for schema hashing: `start_value` is a legitimate, independently-alterable schema property (an `ALTER SEQUENCE RESTART WITH` is itself a schema-affecting DDL operation, distinct from mere consumption), and must be captured — it cannot be assumed to always equal the original `CREATE SEQUENCE START WITH` value.
3. **`ALTER SEQUENCE` cannot change the declared data type.** `ALTER SEQUENCE ... AS BIGINT` fails with error 11711 ("Argument 'AS' cannot be used in an ALTER SEQUENCE statement"), confirmed both experimentally and in the Microsoft Learn remarks ("The data type can't be changed by using the ALTER SEQUENCE statement. To change the data type, drop and create the sequence object."). A type change is therefore only ever observable as a drop+recreate, and will always show up as a `system_type_id`/`user_type_id`/`precision` diff on the same-named object — never as an in-place mutation.
4. **Omitting bounds/start back-fills from the data type's own range, not from a sentinel NULL.** `CREATE SEQUENCE Seq_Defaults AS INT` (no `START WITH`/`MINVALUE`/`MAXVALUE`) produced `start_value = minimum_value = -2147483648` and `maximum_value = 2147483647` — i.e., default start is the type's minimum for an ascending sequence (would be the type's *maximum* for a descending one, per docs). This means a "minimal" `CREATE SEQUENCE` statement and an explicit one that spells out the type's full range are catalog-identical and *should* hash identically — a normalization concern is unnecessary here since the catalog already normalizes at creation time.
5. **Sequences on user-defined alias types resolve through `user_type_id`, not `system_type_id`.** `CREATE TYPE audit_sequences.SeqIdType FROM INT; CREATE SEQUENCE ... AS audit_sequences.SeqIdType ...` produces `system_type_id = 56` (`int`) but `user_type_id` resolves (via `sys.types.user_type_id`) to `SeqIdType`. A query that joins only on `system_type_id` would silently misreport this sequence as a plain `int` sequence and miss a real schema difference if the alias type were later redefined or a different sequence used the raw `int` type instead.
6. **`cache_size` is not a full mirror of what `CACHE`/`NO CACHE` was requested.** Three distinct creation-time states collapse to only two observable `(is_cached, cache_size)` pairs worth noting: `NO CACHE` → `(0, NULL)`; bare `CACHE` (no number) → `(1, NULL)`; `CACHE 50` → `(1, 50)`. The first two share nothing in `cache_size` but are correctly distinguished by `is_cached`; the middle case is inherently unstable across engine versions per Microsoft's own docs disclaimer ("users shouldn't rely upon the selection being consistent... Microsoft might change the method of calculating the cache size without notice"), so a hash that captured a concrete inferred number for bare `CACHE` would be a self-inflicted false-positive source across SQL Server versions/patches — it is correctly NULL/unspecified in the catalog and should stay that way in any hash.

## Version gating

- Sequences themselves (`CREATE SEQUENCE`/`sys.sequences`) were introduced in **SQL Server 2012**, which predates this project's documented minimum supported server (SQL Server 2016 / 13.x) — no gating concern there, sequences are safe to extract unconditionally.
- **`sys.sequences.last_used_value` is documented as "Applies to SQL Server 2017 and later."** This is the one column-level gating fact found. It was not possible to verify live against a 2016 instance (the shared container is SQL Server 2025 Enterprise Developer Edition, build 17.0.1000.7), so this is a documentation-only finding, flagged for follow-up verification against an actual SQL Server 2016 instance before being relied upon in extraction code targeting that floor version.
- All other `sys.sequences` columns used above (`start_value`, `increment`, `minimum_value`, `maximum_value`, `is_cycling`, `is_cached`, `cache_size`, `system_type_id`, `user_type_id`, `precision`, `scale`, `current_value`, `is_exhausted`) are present from the sequence feature's 2012 introduction, per Microsoft Learn's `sys.sequences` reference page — no additional gating documented for those.

## Coverage audit

`SchemaExtractor.ExtractSequencesAsync` and `SchemaHashCalculator.HashSequence` were checked field-by-field against the table above.

Identity (`SchemaName`/`Name`), the resolved data type (joined on `s.user_type_id = ty.user_type_id`, with the same alias-base-type resolution technique used for columns/parameters: correctly using `user_type_id`, not `system_type_id`, matching edge case 5), `precision`, `start_value`, `increment`, `minimum_value`, `maximum_value`, `is_cycling`, `is_cached`, and `cache_size` are all extracted as decimal-string/typed values and hashed unconditionally in `HashSequence`. No `SequenceNormalization` domain exists, so every field always participates at full fidelity. `current_value`, `is_exhausted`, `last_used_value`, `create_date`, `modify_date`, and the raw `object_id`/`schema_id`/`principal_id` are correctly excluded as runtime state or non-deterministic ids, matching the blind doc's own exclusion table. Sequences (`o.type = 'SO'`) are included in the class-1 target-kind filter of `ExtractExtendedPropertiesAsync`, so extended properties on a sequence are captured, not just noted as a theoretical gap.

The one column the blind doc marks "Yes" that isn't extracted is `scale` (`sys.sequences.scale`). This was checked against the criteria for a real gap and does not qualify: the blind doc's own edge case 1 confirms `scale` is an enforced invariant, always `0`, for every legal sequence on every SQL Server version since the feature's 2012 introduction (`decimal`/`numeric` sequences are rejected outright at any scale other than 0). A field that can never differ between two valid sequences can never help detect a schema change, so omitting it carries no risk of masking a real difference. This is unlike, for example, a platform-gated flag that is invariant only on today's supported servers.

No gaps found.
