# User-Defined Table Types

## Catalog views that expose this object type

- **`sys.table_types`** — the primary, authoritative view. One row per user-defined table type. It is a *derived* view over `sys.types` (per Microsoft Learn: "For a list of columns that this view inherits, see `sys.types`"), adding two columns of its own:
  - `type_table_object_id` (`int`) — the `object_id` of a hidden, internally-generated backing object that carries the type's columns/constraints/indexes. Documented as "a foreign key into `sys.objects`... You can use this ID column to query various catalog views, in a way that is similar to an `object_id` column of a regular table."
  - `is_memory_optimized` (`bit`, SQL Server 2014+) — 0 by default; table types are always created with `DURABILITY = SCHEMA_ONLY` (only the schema persists on disk, never data — table type instances are always transient row storage regardless of this flag).
- Inherited from **`sys.types`**: `name`, `schema_id`, `user_type_id`, `system_type_id`, `is_nullable`, `is_user_defined`, `is_assembly_type`, `is_table_type`. **`user_type_id`** (not `type_table_object_id`) is the correct join key for extended properties (see below) and for `sys.types` itself.
- **`sys.columns`**, **`sys.indexes`** / **`sys.index_columns`**, **`sys.key_constraints`**, **`sys.check_constraints`**, **`sys.default_constraints`**, **`sys.computed_columns`**, **`sys.identity_columns`** — all shared verbatim with ordinary tables, keyed by `object_id = type_table_object_id`. This is the mechanism referenced in the codebase's existing extraction design (columns/constraints keyed by `object_id`, with a table's `object_id` and a table type's `type_table_object_id` both landing in the same distribution pass).
- **`sys.extended_properties`** — class `6` = `TYPE` (property on the type itself; `major_id = user_type_id`, `minor_id = 0`), class `8` = `TYPE_COLUMN` (property on a column of the type; `major_id = user_type_id`, `minor_id = column_id`). **Critically, these key off `user_type_id`, not `type_table_object_id`** — the two ids serve different, non-interchangeable roles and mixing them up silently returns zero rows (verified: querying with `major_id = type_table_object_id` returns nothing; `major_id = user_type_id` returns the expected rows).

## Fields/flags relevant to detecting a schema change

### `sys.table_types` / `sys.types` (inherited)
- `name`, `schema_id` — identity. **`schema_id` here is the type's real, user-facing schema** (confirmed: a type created in a custom schema reports that schema's id via `sys.table_types.schema_id`/`sys.types.schema_id`).
- `is_nullable` — always `0` for table types (a table type instance itself can't be null the way a scalar alias type can); not a useful change-detection field but present for schema symmetry.
- `is_memory_optimized` — meaningful once set; toggling it changes physical row format and available index kinds (hash vs. B-tree) and is a genuine schema-shape change.
- `type_table_object_id` — **not itself hash-worthy** (it is a raw catalog object id, non-deterministic across databases, exactly like a table's `object_id`) — only useful as a *join key*, never as a value to include in a hash.

### Columns (via `sys.columns`, keyed by `type_table_object_id`)
Same fields as ordinary table columns: `name`, `column_id`, `system_type_id`/`user_type_id` (data type), `max_length`, `precision`, `scale`, `collation_name`, `is_nullable`, `is_identity`, `is_computed`, `is_ansi_padded`, `default_object_id` (nonzero ⇒ has a default; join `sys.default_constraints`). `sys.identity_columns` gives `seed_value`/`increment_value`/`is_not_for_replication` for identity columns — **but note the CREATE TYPE grammar only allows `IDENTITY (1,1)`** for memory-optimized table types (seed/increment fixed at 1,1); for disk-based (non-memory-optimized) table types, arbitrary `IDENTITY(seed, increment)` values **are** accepted (verified `IDENTITY(1,1)` works on a disk-based type; the memory-optimized grammar block in the docs explicitly pins it to `(1,1)`).
`sys.computed_columns` gives `definition`/`is_persisted` for computed columns.

### Constraints (via `sys.key_constraints`, `sys.check_constraints`, `sys.default_constraints`, all keyed by `parent_object_id = type_table_object_id`)
- `name`, `type_desc`, `is_system_named` — **every constraint on a table type is always system-named (`is_system_named = 1`)**. This is a hard grammar restriction, not a convention: **the `CREATE TYPE ... AS TABLE` grammar has no `CONSTRAINT constraint_name` clause at all** — confirmed both against the official syntax diagram (`<table_constraint>` / `<column_constraint>` productions have no name slot) and empirically: `CONSTRAINT PK_Foo PRIMARY KEY (...)` inside a table type body raises `Msg 156, Incorrect syntax near the keyword 'CONSTRAINT'`, even for a single unnamed column. Only bare `PRIMARY KEY`, `UNIQUE`, `CHECK` (unnamed) are legal. **Foreign keys are entirely unsupported** — `FOREIGN KEY (...) REFERENCES ...` inside a table type body is a syntax error (`Msg 156`), not just disallowed at runtime.
- `is_disabled`, `is_not_trusted` (check constraints) — table types have no `ALTER`, so these are effectively always the CREATE-time values (0/0) and can't drift the way a real table's can via `WITH NOCHECK`/`ALTER TABLE ... NOCHECK CONSTRAINT`. Still worth extracting for symmetry/consistency with the table extractor's constraint records.
- Computed-column primary keys have an extra Engine-enforced rule not present on ordinary tables: the computed column must be `PERSISTED` **and** effectively `NOT NULL`, else `CREATE TYPE` fails with `Msg 1711`.

### Indexes (via `sys.indexes`, keyed by `object_id = type_table_object_id`)
- Every table type object has the same baseline `sys.indexes` row every ordinary table has: `index_id = 0`, `name = NULL`, `type_desc = 'HEAP'`, present whenever there's no clustered index — this is not table-type-specific, just the generic "heap" row, and should be filtered exactly the way the existing table-index extraction already filters it (any extractor keyed on `object_id` picks this up identically for tables and table types).
- Named, explicit `INDEX index_name (...)` table-level indexes **do** support an explicit name (unlike `PRIMARY KEY`/`UNIQUE`/`CHECK`) — confirmed: `INDEX IX_MultiConstraintType_Sku NONCLUSTERED (Sku)` created and reported back verbatim in `sys.indexes.name`, while the `PRIMARY KEY CLUSTERED (...)` and `UNIQUE NONCLUSTERED (...)` on the same type auto-generated system names (`PK__TT_Multi__...`, `UQ__TT_Multi__...`).
- `type`/`type_desc` (CLUSTERED/NONCLUSTERED), `is_unique`, `is_primary_key`, `is_unique_constraint`, `fill_factor`, `is_padded`, `is_disabled` — same semantics as ordinary tables. `sys.index_columns` gives `key_ordinal`, `is_descending_key`, `is_included_column` per usual.
- Requires SQL Server 2014 (12.x)+ per Microsoft Learn — below the library's SQL Server 2016 floor, so this is a non-issue for this codebase's supported range.

### Explicitly excluded (runtime state)
- No row-count/data statistics apply — table types carry no persisted rows outside a live session (`DURABILITY = SCHEMA_ONLY` even when memory-optimized).
- `type_table_object_id` / `user_type_id` themselves (catalog-assigned, non-deterministic across databases) — extract only as join keys, never hash their raw values (same discipline the codebase already applies to ordinary `object_id`/`schema_id`).
- Nothing analogous to `sys.dm_db_index_usage_stats`/`STATS_DATE` applies (no persisted statistics on table types).

## Notable edge cases found by direct experimentation

1. **The backing object is invisible to `sys.tables`.** `type_table_object_id` points to a row in `sys.objects` with `type = 'TT'` / `type_desc = 'TYPE_TABLE'` — **it does not appear in `sys.tables` at all** (`SELECT * FROM sys.tables WHERE object_id = <type_table_object_id>` returns zero rows). Any extraction logic that joins table types to `sys.tables` (rather than `sys.objects`) to pick up shared table-shaped metadata will silently see nothing. Columns/constraints/indexes only work because those views are keyed directly by `object_id`, not by membership in `sys.tables`.
2. **The backing object always lives in the `sys` schema, not the type's own schema.** Verified directly: a type created in `[audit_user-defined-table-types]` (`schema_id = 12`) has a backing `sys.objects` row with `schema_id = 4` (`sys`). The type's *real*, user-facing schema is only available via `sys.table_types.schema_id` (inherited from `sys.types`) — **never** trust the backing object's own `schema_id`.
3. **The backing object has an auto-generated, unpredictable name** of the shape `TT_<TypeName>_<8-hex-digits>` (e.g. `TT_BasicType_5CF6C6BC`) and `is_ms_shipped = 1`, even though the type itself is entirely user-created. Object-level filters that skip `is_ms_shipped = 1` rows (a pattern already used elsewhere in this codebase for the tables/objects extraction) would incorrectly skip every table type's backing object if such a filter were ever applied on this path — the existing codebase design deliberately does not, and this confirms why: it distributes to the table-type container via `type_table_object_id`, not by scanning `sys.objects` directly for user objects.
4. **All table-level constraints are unconditionally system-named** — confirmed empirically that the grammar has no `CONSTRAINT <name>` clause for `CREATE TYPE ... AS TABLE` (Microsoft Learn's own syntax diagram for `<table_constraint>`/`<column_constraint>` omits it entirely, and every one of Microsoft's own examples uses unnamed `PRIMARY KEY`/`UNIQUE`). This makes `is_system_named = 1` a universal invariant for table-type constraints, unlike ordinary tables where it varies. A hash-normalization pass that treats "auto-generated constraint name" as optional/toggleable is effectively **always** in the "normalized" state for table types regardless of the option, since there is no non-system-named alternative to normalize away.
5. **Named table-level `INDEX` clauses are the one exception** — `INDEX index_name (...)` requires and keeps an explicit user name, unlike `PRIMARY KEY`/`UNIQUE`/`CHECK` in the same type body, which are always unnamed and always come out system-named.
6. **No `ALTER TYPE` statement exists at all** (`ALTER TYPE ...` is a flat T-SQL syntax error, `Msg 102`) — a table type can only be dropped and recreated, so there is no notion of an "altered" table type distinct from a differently-shaped one; this matches (and reinforces) the codebase's general model of comparing full catalog snapshots.
7. **Triggers cannot target a table type** — `CREATE TRIGGER ... ON <table_type>` fails with `Msg 8197` ("does not exist or is invalid for this operation"), confirming table types are out of scope for the trigger-extraction pass by construction, not merely by choice.
8. **Foreign keys are a hard syntax rejection**, not merely unenforced — `FOREIGN KEY (...) REFERENCES ...` inside the type body is `Msg 156` (`Incorrect syntax near the keyword 'FOREIGN'`); there is no partial/soft FK support to account for.
9. **A reserved-identifier trap unrelated to table types but worth flagging for anyone scripting test fixtures against this SQL Server 2025 build**: the plain identifier `LineNo` (unquoted, unbracketed) fails to parse as a column name (`Msg 156, Incorrect syntax near the keyword 'LineNo'`) in this specific build, while `LineNum` parses fine — this is evidently a newly-reserved-in-practice token in SQL Server 2025 (not documented in the standard reserved-keywords list at the time of writing); not a table-type-specific behavior, but it broke test-fixture authoring during this audit and is worth remembering.
10. **Memory-optimized table types require a database-level `MEMORY_OPTIMIZED_FILEGROUP`** before `WITH (MEMORY_OPTIMIZED = ON)` succeeds — attempted without one, `CREATE TYPE` fails with `Msg 41337`. This was deliberately *not* provisioned on the shared audit container (to avoid a database-level config change affecting concurrently-running audits against the same container), so `is_memory_optimized = 1` behavior (hash indexes, `NONCLUSTERED HASH ... WITH (BUCKET_COUNT = ...)`, fixed `IDENTITY(1,1)`-only seeding) is documented from the Microsoft Learn syntax reference rather than a live example object in this pass.
11. **Extended properties key off `user_type_id`, not `type_table_object_id`.** These are two different catalog ids serving disjoint purposes on the same logical object: `type_table_object_id` (→ `sys.objects`) is for columns/constraints/indexes; `user_type_id` (→ `sys.types`) is for extended properties and for the type's own catalog identity. Confirmed by direct experiment: `sp_addextendedproperty` at `TYPE`/`TYPE_COLUMN` scope produces `sys.extended_properties` rows with `class = 6`/`class = 8` and `major_id` equal to the type's `user_type_id` — querying with `major_id = type_table_object_id` returns zero rows.

## SQL Server version gating

- `sys.table_types` itself, and the base "table type / table-valued parameter" feature, date to SQL Server 2008 — below this library's SQL Server 2016 floor, so not a live gating concern.
- `INDEX index_name (...)` (table-level named indexes inside `CREATE TYPE ... AS TABLE`) — **SQL Server 2014 (12.x)+**, per Microsoft Learn ("Applies to: SQL Server 2014 (12.x) and later versions, Azure SQL Database, and Azure SQL Managed Instance").
- `is_memory_optimized` column on `sys.table_types`, and memory-optimized table types generally (`WITH (MEMORY_OPTIMIZED = ON)`, hash indexes, `BUCKET_COUNT`) — **SQL Server 2014 (12.x)+**. Azure SQL Managed Instance additionally doesn't support memory-optimized tables/table types on the General Purpose tier.
- All of the above predate this library's documented SQL Server 2016 (13.x) minimum, so none of them represent a live version-gating hazard for the current codebase — every column/behavior described here is available on every server version this library targets.

## Objects created for this audit

Schema `[audit_user-defined-table-types]`:
- `BasicType` — unnamed single-column `PRIMARY KEY`, `DEFAULT` (`sysutcdatetime()`), unnamed `CHECK` constraint; plus a `TYPE`- and `TYPE_COLUMN`-scoped extended property (`MS_Description`) to confirm class 6/8 keying.
- `MultiConstraintType` — composite clustered `PRIMARY KEY`, composite nonclustered `UNIQUE`, and a separately named nonclustered `INDEX` (the one constraint-like clause that keeps its literal name) — exercises the full constraint/index catalog surface together.
- `IdentityType` — `IDENTITY(1,1)` column plus an `NVARCHAR(MAX)` column, to exercise `sys.identity_columns`.
- `NoKeyType` — no constraints/indexes at all (bare heap), to confirm the baseline `index_id = 0` HEAP row behavior.
- `ComputedColType` — `PERSISTED` computed column, to exercise `sys.computed_columns`.

## Coverage audit

No gaps found.

Every catalog field the blind doc identifies as present, queryable, and schema-relevant for user-defined table types is extracted and hashed correctly:

- **Identity/schema fields** — `sys.table_types.schema_id` (resolved via `SCHEMA_NAME(tt.schema_id)`, the type's real user-facing schema, never the backing object's `sys`-schema `schema_id`), `name`, and `is_memory_optimized` are all captured on `UserDefinedTableTypeSchema` (`src/SchemaMetadata.cs`) and hashed in `SchemaHashCalculator.HashUserDefinedTableType` (the `"TYPEKIND:"` block). `type_table_object_id`/`user_type_id` are used only as join keys in `SchemaExtractor`, never hashed as values, matching the doc's explicit guidance.
- **Columns** — the shared `ColumnSelectList`/`ColumnJoins` in `SchemaExtractor.ExtractColumnsAsync` drive both the table and table-type column queries (the latter joins `sys.table_types` to `sys.columns` on `type_table_object_id`), covering `name`, `column_id`, data type (with alias-base-type resolution), `max_length`, `precision`, `scale`, `collation_name`, `is_nullable`, `is_computed`/computed definition/`is_persisted`, and `is_ansi_padded`. Identity (`seed_value`/`increment_value`/`is_not_for_replication`) is captured via a dedicated join in `ExtractUserDefinedTableTypesAsync` and hashed through the shared `HashIdentity`.
- **Constraints** — `sys.key_constraints`, `sys.check_constraints`, and `sys.default_constraints` are extracted through the same object_id-keyed dictionaries used for tables and distributed to `UserDefinedTableTypeSchema.KeyConstraints`/`CheckConstraints`/`DefaultConstraints`, all hashed via the shared `HashKeyConstraints`/`HashCheckConstraints`/`HashDefaultConstraints`. `IsSystemNamed`, `IsDisabled`, and `IsNotTrusted` are all present on the respective records even though they are structurally invariant (always `1`/`0`/`0`) for a table type, matching the doc's "worth extracting for symmetry" note. Foreign keys are correctly never attached to a table type: `ExtractUserDefinedTableTypesAsync` does not accept a `foreignKeysByObjectId` parameter at all, matching the doc's confirmation that `FOREIGN KEY` is a hard syntax rejection inside `CREATE TYPE ... AS TABLE`.
- **Indexes** — `SchemaExtractor.ExtractIndexesAsync` drives from `sys.objects` with `type IN ('U', 'V', 'TT')`, so a table type's inline `INDEX` declarations land in the same object_id-keyed dictionary as table and indexed-view indexes, filtered by `i.name IS NOT NULL` (excluding the baseline unnamed HEAP row exactly as for tables). All fields the doc calls out (`type_desc`, `is_unique`, `is_primary_key`, `is_unique_constraint`, `fill_factor`, `is_padded`, `is_disabled`, `key_ordinal`, `is_descending_key`, `is_included_column`) are captured and hashed through the shared `HashIndexes`, so an explicitly-named `INDEX` clause is preserved verbatim while an auto-generated `PK__`/`UQ__` name is recognized as such by the existing `IsAutoGeneratedName` heuristic when `NormalizeAutoGeneratedNames` is set.
- **Extended properties** — `SchemaExtractor.ExtractExtendedPropertiesAsync` joins class 6 (`TYPE`) to `sys.types` on `ep.major_id = ty.user_type_id` and class 8 (`TYPE_COLUMN`) to `sys.table_types` on `ep.major_id = tt.user_type_id` (with the column-level `SubObjectName` resolved through a further join on `tt.type_table_object_id`), correctly using `user_type_id` rather than `type_table_object_id` as the doc requires. The class-6 filter (`ty.is_table_type = 1`) correctly restricts class 6 to table types, excluding alias/CLR scalar types.

The identity-column memory-optimized-vs-disk-based `IDENTITY(seed, increment)` distinction, the "every table-level constraint is system-named" invariant, the absence of `ALTER TYPE`, and the trigger/foreign-key rejections documented in the "Notable edge cases" section above are all either already reflected correctly in the extraction/hashing logic or are informational facts about SQL Server's grammar with no corresponding code gap (there is nothing to extract for a statement type that cannot exist).
